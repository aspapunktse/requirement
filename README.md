# Requirement & Risk Onboarding

Internal webapp for tracking requirement fulfillment and risk assessment when onboarding a new system or cloud solution into the enterprise.

## Direction: becoming a GRC tool

The app is being developed into a governance, risk and compliance (GRC) tool. The first module is a **requirement database**: Frameworks (ISO 27001:2022 as the base, plus Cybersäkerhetslagen, CSA CCM 4, …), each made up of its own Requirements, all mapped onto one Control Library. Controls are inherited from the Organization or from Provider Systems, compliance is continuous rather than frozen at onboarding, and internal audit can verify Controls through Check-ups. The steering document is [PRD 0001](docs/prd/0001-grc-requirement-database.md), with decisions in [ADRs 0005–0008](docs/adr/).

### What works today

- **Risk Analysis:** on a System's Risks tab, a Risk Owner, a Risk Facilitator or an Admin who isn't the System's owner records a Risk Analysis meeting (date, participants and named outsiders, notes, the open Risks reviewed and new Risks raised in it, and an owner for each Risk, any User), edits it until it is completed, and completes it once every open Risk has an owner; completed analyses show in the System's activity, and a helper answers whether a System has one since a given time, for the stage gates to come.
- **Staged evaluation (both tracks, end to end):** an Admin can switch on "Staged evaluation for new Systems" in Settings (off by default). A staged System starts in its first round on a new Evaluation tab: the owner or an Admin submits it once there is a Business System Owner, a Sensitivity Level that meets its Information Types, a completed Risk Analysis and every mandatory first-round Control has an Assessment. At OG1 the base review and each group with first-round Controls give a Self or Full verdict (any Full means the Full track). On the Self track the owner or an Admin then submits the second round once every mandatory Control has an Assessment and every second-round Document Requirement is provided; a Risk Owner or an Admin who isn't the owner completes a Risk Analysis, which moves the System to OG3. At OG3 the System's Business System Owner (or an Admin who doesn't own it) decides, with a required comment: authorize to operate (the System becomes Approved and can then be marked Onboarded), reject (final: the System is closed and read-only for every role) or send back to an earlier stage; open Risks never block, each decision is in the System's history, and an undecided System shows in the Business System Owner's My tasks. On the Full track the first half also works: at Qualification the Business System Owner says yes, rejects or sends back; the owner then submits the first documentation; every group with a remit on the System (and the base review) gives a Recommendation (recommend, recommend with conditions, advise against) that an owner's edit in its remit reopens; and at OG2 the Business System Owner sees them all and proceeds (with a written justification against an advise-against), rejects or sends back. The Full track's second half reuses the Self track's second round and Risk Analysis, then a second OAG review (the earlier Recommendations stay as history) and OG3, which shows both reviews' Recommendations and needs a written justification to authorize against an advise-against; sending back to or before the first OAG review makes both run again. On an Onboarded System, a change to Framework Scope or classification that adds Controls to a group's remit starts a Change Review: only those groups recommend on the added Controls, the System stays Onboarded, and the Business System Owner accepts or revokes the ATO (sending the System back to a stage they pick); a System without one flags its owner to set one. The classic review routes refuse a staged System. Approved Systems show as ATO everywhere the lifecycle shows (Onboarded stays Onboarded); Systems already in Draft, In Review or Rejected keep the classic review flow, and nothing is moved. The stage cards show their Documentation (first documentation, second round) and the recorded Risk Analysis read-only, with a Risk summary of open Risks by severity and Risk Source; adding links and recording stay on the Documentation and Risks tabs.
- **Onboarding lifecycle:** create a System through a guided interview (one plain question at a time, with the Controls that apply listed beside it by who does the work, and its Framework Scope and Providers set along the way), assess it against the Control Library, log Risks, submit for review (each submission is a Review Round), each Review Step is decided in parallel (a Reviewer the base step, any member of a Review Group that group's step, an Admin any; never the System's owner), the System is Approved once every step has approved and one rejection returns it to Draft, then mark Onboarded. A System In Review shows the round's Review Steps (the base step plus one per Review Group with a Control in its remit, derived live from the Framework Scope; a step that disappears and returns in the same round comes back open, and an approved step reopens, with when and why shown, if a person edits an Assessment of a Control in its remit) and the approval history grouped by round. Decisions show as the group ("GDPR Review Group: Rejected"); only an Admin, Internal Auditor, Compliance Manager and the step's own deciders see who decided. Open steps appear in the deciders' My tasks. A System can name an optional Business System Owner (any User but its owner), picked in the interview or changed on the System page by its owner or an Admin; they can see the System at any stage.
- **About the system:** the first onboarding step asks for name, description, vendor, vendor website, product and plan, vendor trust page, data location, data processing agreement and contract details (reference, renewal date, notice period). A System declaring a Deployment Facet flagged "Needs vendor details" (SaaS to begin with; an Admin sets it in the catalog) must also give vendor name and service URL. The owner or an Admin edits all of it on the System page at any time.
- **Roles:** a dev-only auth stub with a role switcher and server-enforced authorization for nine roles: Admin, Risk Owner, Risk Facilitator, System Owner, Reviewer, Viewer, Business Risk Owner, Compliance Manager and Internal Auditor. Seeing a System never implies writing to it; owner actions belong to the System's owner or an Admin. The owner or an Admin can hand a System to another System Owner, Risk Owner or Admin, one at a time or in bulk from the Systems list. The Risk Facilitator reads every System and the Risk register, runs Risk Analyses (never on a System they own) and assigns Risk owners, and does nothing else on Risks. The Internal Auditor reads everything and writes nothing, even as a System's or Control's recorded owner.
- **Requirement database:** Frameworks (versioned, Draft or Published) own their Requirements, which are linked to Controls by Control Mappings with Full or Partial Coverage. ISO/IEC 27001:2022 is the base Framework, with Annex A and clauses 4–10.
- **Framework import:** `npm run frameworks:load` loads Framework files (Requirements, Control Mappings, Supplementary Controls) as a Draft, idempotently; a Published Framework is only touched with `--allow-published`. The format is in [`prisma/seed-data/frameworks/README.md`](prisma/seed-data/frameworks/README.md).
- **Framework authoring and coverage:** a Compliance Manager, or the Framework Owner for their own non-base Framework (Drafts included), authors Requirements and mappings and publishes a Framework, and can give it a plain-language onboarding question that the System interview asks. A Framework's coverage page (`/frameworks/[id]/coverage`) is a gap ledger: a ring of resolved coverage, stat cards that filter, section tabs, search, "gaps first", and a table of Requirements with their mapped Controls. A Requirement opens a drawer where they map Controls (with suggestions), switches Full and Partial, creates a Supplementary Control, or accepts, edits or un-accepts a gap, and can accept several gaps at once with one justification. Its Download CSV exports the rows in view. The Framework list at `/frameworks` is a catalog table (a library-wide coverage ring, stat cards that filter, search, grouping by family or status, sorting, each Framework's coverage bar, gaps, Systems, Review Group and last change, its version lineage, Publish from the row for a Draft you can curate, Download CSV and Ctrl+K); a Compliance Manager or an Admin adds a Framework on `/frameworks/new`. A Draft is hidden from users who can't see Drafts. Each Framework can have a Framework Owner (any User, assigned by a Compliance Manager or an Admin) who marks which of its mapped Controls are first round, on the coverage page; the owner is shown on the list too and the Control page names the Frameworks that mark it. The marking is stored and shown only, and changes nothing for Systems yet.
- **Control Library:** 118 Controls with Deployment Facet, minimum Sensitivity Level and Impact Level (Integrity, Availability) scoping, a Self-Assessment Question each (Yes fulfils, No opens a linked Risk of source requirement non-conformance, N/A is gated) and a Control Owner. Compliance Managers and Admins create Controls at `/admin/controls`; every role reads it at `/controls`, a workbench with search, filters with live counts, grouping, a drawer per Control listing the Requirements it satisfies, CSV export and, for Compliance Managers and Admins, bulk Assign owner (a Draft Framework stays hidden from roles that can't see Drafts). Each Control has its own page at `/controls/<code>` (tabs for the Control, the Requirements it satisfies, the Organization implementation and the Systems it applies to with the status each shows, Provider and Organization inheritance included), and Compliance Managers and Admins edit one Control at `/controls/<code>/edit`.
- **Applicability:** a Control applies to a System when it is mapped to a Published Framework in the System's Framework Scope and passes the Control's Deployment Facet, minimum Sensitivity Level and Impact Level scoping. A System's Sensitivity Level (1 Public to 5 Critical Sensitivity, set by its owner or an Admin) replaces the old Confidentiality axis, and a System can't be submitted for review without one.
- **Continuous compliance:** classification, Framework Scope and Provider dependencies can change at any lifecycle stage. Those changes, and catalog changes (a Framework published, a mapping or a Control's scoping edited), recompute the System's Control Assessments without touching its onboarding status. Assessments someone worked on are kept as stale and can be removed.
- **Inheritance:** the Organization records its own implementation of each Organizational and Both Control. A System can be a Provider with Full or Shared Control Offerings, and other Systems depend on it. A Control's effective status is resolved live from the System's own Assessment and its sources, never copied, and an Assessment can be reset to inherited. The Organization Control Implementations page shows status by theme and owner, with in-place and bulk editing and each Control's status history.
- **Compliance figures:** each Requirement's status per System (Met, Partially Met, Not Met, Not Applicable) is derived from the effective status of its mapped Controls. The Compliance Percentage is Met ÷ applicable Requirements for one Framework, pooled across Systems.
- **Internal Audits:** an Internal Auditor plans a draft audit (target Controls, Systems picked by hand or by filter, whether the Organization is included, a due date), writes each Control's questions and launches it. Launching generates one Check-up per applicable System and Control, plus one per Organizational or Both Control when the Organization is included, and freezes the audit. A Check-up appears in its recipient's "My tasks" (the System's owner, or the Control Owner), marked overdue after the due date; the recipient answers each question Yes / No / N/A with a description and evidence links, which changes no status. An Internal Auditor evaluates each answered Check-up as Conforming, Observation or Nonconformity with a comment; the evaluation is final, freezes the response, is readable by the recipient and writes one System-less Change Event. A Nonconformity also opens a Risk linked to the Check-up (on the System, or one Organization Risk with no System, which Risk Owners and Admins manage and the Internal Auditor reads) and sets a Fulfilled target back to In Progress as `"system"` (a System that is Fulfilled only through inheritance gets its own In Progress override), reaching inheriting Systems live. An Internal Auditor can withdraw a Check-up that isn't evaluated, with a reason (final; it leaves the recipient's tasks and can't be answered or evaluated, but keeps any response), and close a launched audit once every Check-up is evaluated or withdrawn; closing is refused while any is open, naming which. A closed audit and everything in it is read-only for every role. The audit list shows Draft / Launched / Closed, and the audit page shows progress (sent, answered, evaluated, withdrawn, overdue), each response, outcome and withdrawal. Only an Internal Auditor writes, evaluates, withdraws or closes; Admin, Compliance Manager and Risk Owner can read audits.
- **Statement of Applicability:** a page every role reads in the Home look: a hero with an included-of-all ring, four cards that filter, view tabs (All, Included, Excluded, Missing justification, Not started anywhere), search, Framework and Applies-to filters, grouping by domain, source or implementation, and a table with a Control drawer. Every Control is listed with whether it is included (applies to the Organization or to at least one System, derived live, never stored), a justification generated from its Published Framework mappings, and its implementation (the Organization's status and a rollup across all Systems; the drawer names only the Systems the user can see). A Compliance Manager or an Admin writes, edits and clears the exclusion justification of an excluded Control in the drawer (a Change Event per change); excluded Controls without one are flagged "justification missing". Download view exports the rows on screen as CSV; Download full Statement exports every Control. Export for audit opens the whole Statement as a print-ready document with a cover (Organization, who and when, the Published Frameworks, counts) and opens the print dialog to save it as a PDF.
- **App header:** on every page after sign-in, the main navigation (Home, Systems, Information Types, Document Requirements, Controls, Risks, Check-ups, Internal Audits, SoA, Frameworks, then My Business Risks for a Business Risk Owner and an Admin menu of the Admin pages for an Admin) with the current part of the app marked, showing only the pages the acting role may open, collapsing to a menu on narrow screens; a "Jump to" button and Ctrl+K open the one palette, which lists the page's own items first and then the pages to go to; a Theme menu (Register, High contrast, Parchment, Slate and Forest, each with its own colours and fonts, previewed on hover or focus, also in the palette), a System / Light / Dark Mode switch (both remembered in the browser and applied before first paint) and the acting user (the role switcher with the dev stub) are on the right. Every colour in the app comes from the theme's tokens.
- **Views:** a role-differentiated `/home` command center (a "your move" ring, headline figures with weekly sparklines (exact from the daily snapshots a Vercel cron records, derived from timestamps before that) that filter "My tasks" grouped by urgency, a picture of the role's world, shortcuts, recent activity and the Ctrl+K jump palette), the Systems list at `/systems` (a register table: status ring and saved-view cards with trend lines from the daily snapshots, status tabs, search, filters, grouping, sorting, paging, row selection with CSV export and a bulk Change owner and, for an Internal Auditor, Add to Internal Audit (Draft audits only), Ctrl+K jump; its "stale Draft" age and "Under N% met" percentage are Admin settings), the System page, a cockpit (a header with the lifecycle, the next step for the acting user and headline figures; pinned tabs kept in the URL hash; an Overview of Compliance, Controls, Needs attention, Risks, Classification and Recent activity tiles; a Controls tab that groups the System's Controls by category with search and an All / To do / In progress / Done / Inherited filter, and opens each Control in a drawer, linkable as `#controls/<code>`, for its answer, status, evidence, notes and Assessment Queries; a Requirements tab with a card per Framework (ring, counts, the Requirements not met); a Risks tab with the register (each Risk shows its Risk Source, filterable, and an Admin, Risk Owner or Risk Facilitator can make any User its owner, also from the Risk Analysis; the new owner gets the Risk in My tasks, linking to it as `#risk-<id>`), its grid and Log Risk; a Providers tab with where the Controls come from, a card per Provider dependency and the System's own side as a Provider; a Documentation tab listing the Document Requirements that apply, by stage, each provided or not with its link or uploaded file (its owner or an Admin adds a link and/or one file of up to 4 MB, kept in the database, and marks it provided; anyone who sees the System downloads it); a Profile tab with About (its owner or an Admin can edit the name, vendor and description), Deployment Facets, Sensitivity Level, Impact Level, Business Units and Framework Scope; and an Approval and activity tab with the approval panel and a timeline of every Change Event), a read-only Risk register at `/risks` (every Risk the acting user may see across Systems, plus Organization Risks for the roles that read them, with Risk Source, status and severity filters kept in the URL; the Business Risk Owner's Risk queue filters by source too), the Business Risk Owner's scoped dashboard and System Portfolio, and the Organization Control Implementations page.
- **Assessment Queries:** non-blocking question threads on one Control Assessment.
- **Change Events:** a curated log of compliance-relevant changes, shown as Recent activity on Home and as the timeline on a System's page (including when a System was created and when a Risk was logged on it); both hide the person behind a Review Step decision or a Query from those who may not see them.
- **Information Types:** a catalogue at `/information-types` that every role reads (each type's Sensitivity Level and how many Systems declare it) and the Compliance Manager or an Admin curates. A System's owner or an Admin declares the types it handles on the Profile tab and in the onboarding interview, and its Sensitivity Level can't be set below the highest of them (adding a higher type offers to raise the level in the same save); a System whose type was later raised is flagged "below its Information Types" and can't be submitted for review until its level is raised. A type can also suggest Frameworks: the owner adds a suggested Framework to the System's scope in the interview or on the Profile tab, or leaves it out, and a System with suggestions still to decide is flagged "Suggested Frameworks to review" (never blocking a submit). A "Where can I put this information?" view (`/information-types/where`, every role, the Systems it can see) shows, for a type, the Systems that declare it, may hold it (level at or above) or are below it, and the Systems list shows each System's types and the flag, with a "declares any of" Information Type filter and "Below its Information Types" and "Suggested Frameworks to review" cards.
- **Document Requirements:** a catalogue at `/document-requirements` of what a System must provide besides answering its Controls (an architecture description, a DPIA), each with the stage that needs it (first documentation or second round) and the Tracks it applies to (Self, Full or both; first documentation is Full only). Every role reads it and the Compliance Manager or an Admin curates it. A System's owner or an Admin records a link or a file and marks each one provided on the System's Documentation tab; every Document Requirement applies until Systems have a Track, and a helper answers whether all of a stage's are provided, for the stage gates to come.
- **Admin catalogs:** Deployment Facets, Business Units, Frameworks, users and Business Risk Owner assignments.
- **Review Groups:** an Admin creates named groups of Users (any role but Internal Auditor) and manages their members; an Admin or Compliance Manager ties a group to non-base Frameworks (a Framework has at most one group), and a tied group with no members is flagged. A tied group adds a Review Step to Systems In Review that have one of its Frameworks in scope, and its members can decide that step, see every System (any status) with one of its Frameworks in scope, and raise and resolve Assessment Queries on Controls in its remit; their Query Messages show as the group ("Base review" for a Reviewer), by the same rule as step decisions.
- **Settings:** an Admin changes the Systems list's two thresholds and the Organization name (named on the audit export) at `/admin/settings` (page built to take more settings); each change records who and when and shows in Recent activity. The same page edits the five Sensitivity Levels' labels, descriptions and colours (checked for 4.5:1 contrast, dark colours derived; not a Change Event); the colours are published as `--rg-sensitivity-<n>-fg/-bg` tokens read from the database on each request, so a rename shows everywhere. The `SensitivityChip` shows a level on the Systems list (own sortable column and a filter, Not set included, kept in the URL), the System page header, the owner's and onboarding pickers (chip plus description), and as "From <level>" on Controls in the Control Library, the Control drawer and the Compliance Manager's editor.
- **Design proposals:** browsable at `/design`, with interactive alternatives for onboarding, the Systems list, System detail, the Control Library, an Enterprise Control Library alternative, the Statement of Applicability, Home by role, creating an Internal Audit, the Framework list, a Framework's coverage page, the Deployment Facet catalog and the Organization Control Implementations page, the staged evaluation view on the System page, and anonymous thumbs-up voting per proposal.
- **Pipeline:** CI on every pull request, and CD to Vercel production gated on green CI (see CI/CD below).

## Stack

- **Node.js 24** — the version production (Vercel) runs. It is set once in `package.json` (`"engines": { "node": "24.x" }`); CI and the CD deploy job read it from there (`node-version-file: package.json`), and the `Dockerfile` mirrors it (`node:24-alpine`), so keep the two in step

- **Vitest + Testing Library** — unit/integration tests

- **GitHub Actions** — CI on every PR, CD on merge to `main`; jobs run on `ubuntu-latest` and the actions are pinned to major tags that run on Node 24

## Getting started

You need Node.js 24 (see `engines` in `package.json`), Docker (for the local Postgres) and npm.

```bash
cp .env.example .env
docker compose up -d db
npm install
npx prisma migrate dev
npx prisma db seed
npm run dev
```

App runs at http://localhost:3000, health check at `/api/health`.

## Seeding a Vercel deployment

The seed script (`prisma/seed.ts`) is meant to run **once, from your machine, against the production database** — not as part of Vercel's build step, since a build can re-run and you don't want the seed firing repeatedly against prod.

```bash
npm i -g vercel        # if you don't have the CLI yet
vercel link            # link this checkout to the Vercel project, once
npm run vercel:env:pull  # writes .env.production.local (gitignored)
npm run prisma:seed:prod
```

Make sure `prisma migrate deploy` has already been run against that same database first (the Vercel project's build command is `npx prisma migrate deploy && npm run build`, so every production deploy applies pending migrations automatically; you can also run it manually with the same `.env.production.local`). Check `prisma/seed.ts` before re-running it against a real environment — it upserts most rows, but confirm it won't create duplicate demo data if run twice.

## CI/CD

- **Node version:** CI, the CD deploy job and the Docker image all run Node 24, the same as production. The workflows read it from `engines.node` in `package.json`; the `Dockerfile` can't, so it carries a matching `node:24-alpine`.
- **`.github/workflows/ci.yml`** runs on every pull request and push to `main`: lint, typecheck, unit tests against a real Postgres service container, production build, and a Docker build check. `react-hooks/set-state-in-effect` is currently downgraded to `warn` in `eslint.config.mjs` (8 existing components fetch in effects) so lint can pass — tracked in #63. Nothing in GitHub *enforces* CI on merge (see below), so the CD gate is what actually protects production.
- **`.github/workflows/cd.yml`** runs after CI succeeds on `main`: builds and pushes the production image to GitHub Container Registry (`ghcr.io/<owner>/<repo>`), then a `deploy` job (gated by the `production` GitHub Environment) deploys that commit to Vercel with the Vercel CLI (`vercel deploy --prod`; Vercel builds remotely, so its project env vars like `DATABASE_URL` stay in Vercel). Vercel's own Git auto-deploy is disabled for `main` in `vercel.json` so production only ships from a green commit; other branches still get Vercel preview deployments. **Migrations run only in production:** the Vercel project's build command is `if [ "$VERCEL_ENV" = "production" ]; then npx prisma migrate deploy; fi && npm run build`, and `DATABASE_URL` is set for the Production environment only. So a preview builds without touching any database, and its pages have no database at runtime. (The workflow doc has the history of why.) The Neon Vercel integration still creates a `preview/<git-branch>` Neon branch per preview. Neon's free plan caps a project at 10 branches and doesn't delete merged ones, so clear old `preview/*` branches in the Neon console from time to time. When the cap is hit, new previews fail with "Resource provisioning failed". Requires a `VERCEL_TOKEN` secret (the org/project IDs are in the workflow file).

### Repo settings

- Branch protection/rulesets aren't available on this private, free-plan repo, so a red CI run can't block a merge. Production is still safe: the `deploy` job only runs after CI succeeds. If the repo moves to GitHub Pro (or goes public), protect `main` and require the CI workflow plus PR review.
- Add a `production` GitHub Environment with required reviewers if deploys should be gated by human approval.
- Set the `VERCEL_TOKEN` secret (on the `production` environment or repo-wide) for the deploy step — do not commit it.
