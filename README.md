# Requirement & Risk Onboarding

Internal webapp for tracking requirement fulfillment and risk assessment when onboarding a new system or cloud solution into the enterprise.

## Direction: becoming a GRC tool

The app is being developed into a governance, risk and compliance (GRC) tool. The first module is a **requirement database**: Frameworks (ISO 27001:2022 as the base, plus Cybersäkerhetslagen, CSA CCM 4, …), each made up of its own Requirements, all mapped onto one Control Library. Controls are inherited from the Organization or from Provider Systems, compliance is continuous rather than frozen at onboarding, and internal audit can verify Controls through Check-ups. The steering document is [PRD 0001](docs/prd/0001-grc-requirement-database.md), with decisions in [ADRs 0005–0008](docs/adr/).

**Milestone 1 (model split) has landed:** the rename of the old `Requirement` concept to **Control** (#70, [ADR 0005](docs/adr/0005-split-requirement-and-control.md)) — the code now says `Control`, `ControlAssessment`, `AssessmentQuery`, `/admin/controls` and `/api/controls` — the Compliance Manager role (#71), Framework-owned **Requirements** linked to Controls by **Control Mappings**, with ISO/IEC 27001:2022 Annex A migrated as the base Framework (#72), Framework authoring — Requirements, the Control Mapping editor and Draft/Published (#73), the Framework Coverage view with gap acceptance and Supplementary Controls created from gaps (#74), and the ISO/IEC 27001:2022 clauses 4–10 as Requirements with Supplementary Controls (#75). What's still missing is the rest of the target model — the code still has `Capability` where [`CONTEXT.md`](CONTEXT.md)'s *target* vocabulary has **Provider** (Regulatory Overlay is gone since #88: each overlay became a Framework). Each glossary entry's historical note maps new terms to the names still used in code. The "Project status" section below describes what's actually built today, using the code's current names. Work proceeds in the PRD's five milestones (model split → applicability → inheritance → content & SoA → internal audit). **Milestone 2 (applicability & continuous compliance) was cut into issues #85–#90, all of which have landed** (after #91, the owner-rule follow-up to #78, which has landed). **Milestone 3 (inheritance) is under way**: its GitHub milestone is cut into issues #119–#126 and the first two, the Control Owner (#119) and the Organization Control Implementation (#120), have landed; the order and the supervised Sonnet-sub-agent workflow used to deliver them are in [`HANDOFF.md`](HANDOFF.md) and [`docs/agents/supervised-workflow.md`](docs/agents/supervised-workflow.md).

What exists and works:
- Next.js/Prisma/Postgres scaffold, Docker, and a CI → CD → Vercel production pipeline gated on green CI (see CI/CD below)
- Dev-only auth stub with a role switcher and server-enforced authorization for all 7 roles (`ADMIN`, `RISK_OWNER`, `SYSTEM_OWNER`, `REVIEWER`, `VIEWER`, `BUSINESS_RISK_OWNER`, `COMPLIANCE_MANAGER`)
- The `COMPLIANCE_MANAGER` role (#71, PRD 0001 §5): curates the requirement database — creates and edits Controls in the Control Library (`/admin/controls`, `/api/controls`) and the Framework catalog (`/admin/frameworks`, `/api/frameworks`), alongside `ADMIN`, who stays a superuser. Reads every System in every status (full visibility, like `ADMIN`/`RISK_OWNER`/`REVIEWER`) but is strictly read-only there: every System, Assessment, Risk, Assessment Query, lifecycle and classification mutation returns 403 server-side, and the System pages hide the matching controls. The Deployment Facet, Capability and Business Unit catalogs and Business Risk Owner assignment stay `ADMIN`-only. Its `/home` shows a Controls/Frameworks stat-strip and "Where to start" tiles for the Control Library, Frameworks and Systems; seeded as `compliance-manager@example.com`
- System write permissions (#78): seeing a System never implies writing to it. Editing a Control Assessment or answering a Self-Assessment Question is the System's owner or `ADMIN`; a `RISK_OWNER` who isn't the owner may additionally do only the waive-gated transitions (set Waived / Not Applicable, answer N/A), which still need a justification note on a mandatory Control. A `RISK_OWNER` who *owns* the System can't waive a **mandatory** Control on it, nor answer its Self-Assessment Question N/A (#97): another Risk Owner or an `ADMIN` has to (403 server-side; the UI hides those options). They may still waive non-mandatory Controls and keep every other owner action, and an `ADMIN` may waive anything, including on a System they own (the one rule is `waiveRefusal` / `canWaiveControl`). Submitting a System for review is the owner or `ADMIN`. Every other role (`REVIEWER`, `VIEWER`, `BUSINESS_RISK_OWNER`, `COMPLIANCE_MANAGER`, and any future role) gets 403 server-side, and `/systems/[id]` hides the matching controls (Assessment edit form and Self-Assessment buttons, Submit for review; a non-owner Risk Owner sees only the Waived / Not Applicable / N/A affordances). The rules live in `src/lib/system-permissions.ts`; the routes check authenticate -> System visible (404) -> permission (403) -> validation. Assessment Queries are unaffected (Reviewer/Risk Owner/Admin raise and resolve, the owner replies)
- One owner rule and restricted System creation (#91): "the System's owner" is whoever `ownerId` names, **whatever their role** (except a `COMPLIANCE_MANAGER`, who stays read-only even when recorded as owner), and every owner action goes through `isSystemOwnerOrAdmin` in `src/lib/system-permissions.ts`. That now covers changing classification (Deployment Facets, Impact Level), declaring Capabilities, Business Units and Framework Scope, logging a Risk, and marking Onboarded, on top of editing Assessments and submitting; the per-feature `canX` helpers delegate to it and, since #86, have no lifecycle checks of their own (classification, Capabilities and Framework Scope are changeable at any stage; `canMarkOnboarded` still needs an Approved System). An owning `RISK_OWNER`, `REVIEWER` or `VIEWER` can therefore do all of those, and a `SYSTEM_OWNER` who doesn't own a System can do none (the `onboard` route no longer has a role gate of its own). Role grants that aren't about ownership are unchanged: a `RISK_OWNER` logs Risks on any System and changes Risk status, a Reviewer approves, Reviewer/Risk Owner/Admin raise and resolve Assessment Queries. Only `SYSTEM_OWNER`, `RISK_OWNER` and `ADMIN` may create a System (`canCreateSystem`: `POST /api/systems`, `/systems/new` and the "New System" button; everyone else gets 403 and no entry point), and the creator becomes the owner. A non-owner `RISK_OWNER` (waive-only) who sends a changed `evidence` on `PATCH …/assessments/[controlId]` gets 400 and nothing is written, rather than the field being silently ignored
- Framework Requirements and Control Mappings (#72, [ADR 0005](docs/adr/0005-split-requirement-and-control.md), PRD 0001 F-FW.1–3, F-CL.1–2, F-CL.4): a `Framework` now has a `version` (name + version is unique), an optional `supersedesId`, a `licensing` flag (`PARAPHRASE_ONLY`/`QUOTABLE`), `isBase`, and a `DRAFT`/`PUBLISHED` `status`; it owns its own `Requirement` rows (code unique per Framework, section, title, text), which are linked many-to-many to Controls by `ControlMapping` (`FULL`/`PARTIAL` coverage, optional rationale, one mapping per Requirement + Control pair). A Control records an optional `originFrameworkId` (set = Supplementary Control, null = base Control), and the old direct `Control.frameworks` tag is gone. Exactly one Framework is the **base Framework** — **ISO/IEC 27001:2022**, `PUBLISHED`, paraphrase-only, with 93 Annex A Requirements each mapped `FULL` 1:1 to the Control with the same code (enforced in application code, see `src/lib/frameworks.ts`, not by a partial unique index Prisma can't represent); the hand-written migration `20260929150000_add_framework_requirements_and_control_mappings` migrated the existing data (keeping the Framework row's id, so Framework Scope and Business Risk Owner assignments survive) and the seed produces the same shape on a fresh database. Any other Framework becomes a `DRAFT` with its old Control tags dropped. `getComplianceForSystems(..., { frameworkId })` now narrows to Controls mapped to a Requirement of that Framework (a like-for-like substitute for the old tag; the Requirement-based percentage is milestone 2). `ChangeEvent.systemId` is nullable and `CONTROL_MAPPING_CHANGED`/`FRAMEWORK_PUBLISHED` exist for System-less events (emitted since #73, see below). `/admin/controls` shows a read-only "Satisfies: ISO/IEC 27001:2022 A.8.24, …" line derived from mappings instead of a Framework picker
- Framework authoring (#73, PRD 0001 F-FW.4–5, F-CL.4, F-CL.7, F-CE.1): a Compliance Manager (or Admin) creates a **Draft** Framework at `/admin/frameworks` (name, version, supersedes, licensing, `strictComplianceRequired`; the same screen edits them, shows a Draft/Published status badge and has a one-way **Publish** action behind a confirm), and authors it on the per-Framework page `/admin/frameworks/[id]`: Requirements grouped by section with create/edit/delete (code, section, title, text — a visible "own-words paraphrase, no verbatim text" hint on `PARAPHRASE_ONLY` Frameworks), and under each Requirement a Control Mapping editor (searchable Control picker, Coverage Full/Partial, optional rationale; add, change Coverage, remove). The Control edit view (`/admin/controls`) lists the reverse view: every Requirement mapped to that Control, across Frameworks. **Draft Frameworks are invisible outside `COMPLIANCE_MANAGER`/`ADMIN`:** `GET /api/frameworks` filters them out, `GET /api/frameworks/[id]` and its `/requirements` are a 404, a Control's mappings into a Draft are left out of `/api/controls`, and every write on the routes below is a 403 for anyone else. A Draft can't be added to a System's Framework Scope (`POST /api/systems/[id]/framework-scopes` returns 400, and the picker hides it); scope rows that already point at a Draft (left over from the #72 migration) are untouched. Publishing (`POST /api/frameworks/[id]/publish`) is Draft → Published only, records a System-less `FRAMEWORK_PUBLISHED` Change Event and then calls the single hook `onFrameworkPublished` in `src/lib/frameworks.ts`, which since #87 recomputes applicability for Systems that already have the Framework in scope (see the catalog-change recompute bullet below). The base Framework can't be retired or moved back to Draft, but its Requirements are editable. Every mapping add / remove / Coverage change (a rationale-only edit is not) records a System-less `CONTROL_MAPPING_CHANGED` Change Event, actor = the acting user, detail e.g. `Control Mapping changed: Requirement ISO/IEC 27001:2022 A.8.24 ↔ Control A.8.24 (FULL → PARTIAL)`; deleting a Requirement that has mappings logs one `removed` event per mapping (`…; Requirement deleted`). Routes: `GET/POST /api/frameworks/[id]/requirements`, `PATCH/DELETE …/requirements/[requirementId]`, `POST …/requirements/[requirementId]/mappings`, `PATCH/DELETE …/mappings/[mappingId]`, `POST /api/frameworks/[id]/publish`, plus `GET /api/frameworks/[id]`. Since #87, changes to mappings on a Published Framework reach the Systems right away (see the catalog-change recompute bullet below)
- Framework Coverage view, gap acceptance and Supplementary Controls from gaps (#74, PRD 0001 F-OUT.1, F-CL.2, F-CL.5–6, F-FW.6): the gap-analysis tool. **Coverage rule:** a Requirement is *covered* iff it has at least one `FULL` Control Mapping; no mappings, or only `PARTIAL` ones (several Partials never add up to Full), make it a **Coverage Gap**; a gap a Compliance Manager/Admin has accepted with a justification is an **Accepted gap** (shown separately, counted as resolved). `/frameworks` (every signed-in user) lists the visible Frameworks with `covered/total · gaps · accepted` counts and links to `/frameworks/[id]/coverage`, the Coverage view: every Requirement grouped by section with its mapped Controls, each mapping's Coverage and its derived state, header counts (total / covered / gaps / accepted) and a filter (all / gaps only = open gaps / accepted gaps only). Published Frameworks are read-only for everyone signed in; a Draft is invisible ("Framework not found") outside `COMPLIANCE_MANAGER`/`ADMIN`, who additionally get the actions on gaps. `/admin/frameworks` shows the same counts per Framework and links to the Coverage view; `/home` has a "Framework coverage" tile for every role. The derivation is pure (`src/lib/coverage-state.ts`) plus queries in `src/lib/framework-coverage.ts`; the base ISO/IEC 27001:2022 Framework shows 118/118 covered (Annex A plus clauses 4–10, see #75 below), 0 gaps. **Accept gap:** `Requirement` gains `gapAcceptedAt`, `gapAcceptedById`, `gapJustification` (migration `20260929160000_add_requirement_gap_acceptance`); `PUT /api/frameworks/[id]/requirements/[requirementId]/gap-acceptance` (a non-blank justification is required; accepting again replaces it; a covered Requirement is a 409) and `DELETE` (un-accept, clears all three; 409 if not accepted), `COMPLIANCE_MANAGER`/`ADMIN` only. Adding a `FULL` mapping (or upgrading one to Full) clears any acceptance, so a Requirement that later loses its Full mapping comes back as an open gap rather than a stale "Accepted gap". Acceptance is not a Change Event (PRD F-CE.1 doesn't list it). **Supplementary Control from a gap:** the "Create Supplementary Control" action on a gap opens the Control form (shared with the Control Library, `NewControlFields`) and `POST …/requirements/[requirementId]/supplementary-control` creates the Control with `originFrameworkId` set to the Framework and a `FULL` mapping to the Requirement in one transaction, logging the same `CONTROL_MAPPING_CHANGED` event as the mapping endpoint (a duplicate Control code is a 409 and leaves nothing behind; a covered Requirement is a 409). `/admin/controls` badges a Supplementary Control with its origin Framework (`Supplementary · NIS2:2022`) and can filter all / base / Supplementary; a Draft origin Framework is hidden from users who can't see Drafts. Other routes: `GET /api/frameworks/[id]/coverage`; `GET /api/frameworks` carries a `coverage` summary per Framework
- ISO/IEC 27001:2022 clauses 4–10 (#75, PRD 0001 F-FW.3, [ADR 0005](docs/adr/0005-split-requirement-and-control.md)): the base Framework now covers the management-system clauses as well as Annex A — 25 clause Requirements (4.1–4.4, 5.1–5.3, 6.1.1–6.1.3, 6.2, 6.3, 7.1–7.5, 8.1–8.3, 9.1–9.3, 10.1, 10.2; 7.5, 9.2 and 9.3 are single Requirements rather than split into 7.5.1–7.5.3 etc.), each with `section` = its clause group heading and `text` an own-words paraphrase (ISO text is licensed, nothing verbatim), and one **Supplementary Control** per clause (`ISMS-<clause>`, e.g. `ISMS-4.3` "ISMS scope defined and maintained": `ORGANIZATIONAL`, mandatory, origin Framework ISO/IEC 27001:2022, no question, so never assessed per System and no System's Assessments are created or changed) `FULL`-mapped to it. Eight clauses also carry a `PARTIAL` mapping with a rationale to an Annex A Control that partly serves them (4.2↔A.5.31, 5.1↔A.5.4, 5.2↔A.5.1, 5.3↔A.5.2, 7.2 and 7.3↔A.6.3, 7.5↔A.5.37, 9.2↔A.5.35). Delivered as `prisma/seed-data/iso27001-clauses.json` (shaped like the PRD F-IMP.1 import sketch: `framework`, `supplementaryControls`, `requirements` with `mappings`), loaded idempotently by `prisma/seed.ts` after the Annex A step (everything upserted by natural key without overwriting, so curated rows survive a re-seed), plus the hand-written data migration `20260929170000_add_iso27001_clause_requirements` for existing databases (selects the base Framework by `isBase`, does nothing if there is none, every insert `ON CONFLICT DO NOTHING`). `src/lib/__tests__/iso27001-clauses-seed.test.ts` checks the JSON (unique codes, every clause has a `FULL` mapping, mapped Controls exist, `ISMS-` `ORGANIZATIONAL` Controls, rationales on Partials) and that the migration SQL carries exactly the same content
- The full onboarding lifecycle: create a System → assess it against the Control Library → log Risks → submit for review → a Reviewer's Approve/Reject decision (Rejected returns to Draft, not a dead end) → mark Onboarded
- The Control Library (`/admin/controls`): the 93-control ISO 27001:2022 Annex A seed, Deployment Facet-based scoping (a System declares one or more facets — e.g. On-Prem, Cloud — and Hybrid is simply declaring more than one, not its own catalog entry), self-declared CIA Impact Level thresholds (Confidentiality/Integrity/Availability, each an independent Low/Moderate/High/Critical axis a Control can set a minimum on), the per-Control Self-Assessment Question (Yes auto-fulfills, No auto-opens a linked Risk, N/A is Admin/Risk-Owner-gated), and Capability declaration that auto-fulfills mapped Controls and reverts them on removal (unless a human has since touched the Assessment) — see [ADR 0003](docs/adr/0003-multiselect-deployment-facets-plus-overlays.md)
- Changing a System's classification (Deployment Facets or Impact Levels) — declared Deployment Facets or Impact Level thresholds — at any lifecycle stage (#86) recomputes its applicable Control set (a single diff against the combined old vs. new classification) without discarding work already done: newly-applicable mandatory Controls get `NOT_STARTED` Assessments, no-longer-applicable untouched ones are removed, and no-longer-applicable *touched* ones are left in place as stale for the owner to resolve
- Continuous compliance (#86, [ADR 0006](docs/adr/0006-continuous-compliance-replaces-draft-lock.md), PRD 0001 F-AP.2, F-AP.4, F-AP.5): the Draft-only lock is gone. The System's owner or an Admin can change Deployment Facets, Impact Levels, Capabilities and Framework Scope at **any** lifecycle stage (In Review, Approved, Onboarded included); the six `canX` helpers no longer look at `status`, and `PATCH /api/systems/[id]` lost its "Only a Draft System's classification can be changed" 400. Every change goes through the same recompute (`diffApplicabilityOps` in one transaction; Capability changes auto-fulfil or revert Assessments) and writes only the classification and Assessment rows: it **never** changes `System.status`, `onboardedAt` or Approval history, so an Approved or Onboarded System stays that way. The submission check (Draft to In Review) is unchanged. The newly Not Started mandatory Controls count against the System's compliance figures automatically (`getComplianceForSystems` derives from applicable Controls) and show up in the owner's "My tasks": `getSystemsNeedingAttention(ownerId)` (`src/lib/dashboard.ts`) now also looks at the owner's non-Draft Systems and returns `needs-assessment` (with `count` = applicable mandatory Controls with no touched Assessment, shown as "N Controls need assessment" on the System's row) and, for a Draft or non-Draft System alike, `stale`; a non-Draft System can carry both reasons, one task row each. Draft behaviour (`rejected`, `stale`) is unchanged. Tests: `src/app/api/systems/__tests__/continuous-compliance.test.ts` (every mechanism x In Review/Approved/Onboarded x owner/Admin, non-owner refusals with no DB change, status/`onboardedAt`/Approval history untouched, compliance and My tasks deltas) plus updated per-mechanism route tests
- Removing a stale Control Assessment (#109, follow-up to #86): a **stale** Assessment (its Control no longer applies, but someone worked on it, so a recompute kept it) can now be cleared; before this the owner's "Stale assessment" task never went away unless the classification change was reverted. `DELETE /api/systems/[id]/assessments/[controlId]` removes the row (`removeStaleAssessment` in `src/lib/control-assessments.ts`), allowed to the System's owner or an Admin only (`isSystemOwnerOrAdmin`; a Compliance Manager stays read-only, everyone else gets 403). It answers 404 when there is no such Assessment, **409 when the Control still applies** (a live Assessment is never deleted; set its status instead) and **409 while an Assessment Query on it is still open** (resolve the Query first; the check is part of the delete itself, so a Query raised in the meantime can't be cascaded away). The delete and a Change Event go in one transaction. New action `ChangeEventAction.ASSESSMENT_REMOVED` (migration `20260930110000_add_assessment_removed_change_event`, `ALTER TYPE ... ADD VALUE`, no data change), kept apart from `ASSESSMENT_STATUS_CHANGED` so the log tells a removal from a status change; actor is the acting user, detail e.g. `Stale Assessment for A.7.8 removed (was Fulfilled; evidence: "…"; notes: "…"; 1 resolved Query removed with it)` (evidence and notes truncated at 200 characters, omitted when empty). Resolved Assessment Queries and their messages cascade with the row and only their count is kept in the event; Risks opened from the Assessment survive, unlinked. The System page's "No Longer Applicable" section shows a **Remove** button (with a confirm) on each stale Assessment to the owner or an Admin (the shared `isSystemOwnerOrAdmin` helper), or a note instead of the button while a Query on it is open. Removing the last stale row on a System clears its "Stale assessment" task from "My tasks" with no further code. Tests: `src/app/api/systems/[id]/assessments/[controlId]/__tests__/delete.test.ts` and `src/components/__tests__/ControlAssessmentList.test.tsx`
- Capability auto-fulfilment in every recompute path (#110): declaring a Capability already auto-fulfilled the applicable Controls it is mapped to; now a Control that becomes applicable **later** does too. Every path that creates Assessment rows (`changeSystemClassification`, `applyFrameworkScopeDeclared`/`applyFrameworkScopeRemoved` and the catalog recompute `finishRecompute`) goes through one shared piece in `src/lib/capability-fulfillment.ts`: `planNewAssessments` turns a System's newly applicable Control ids into the create rows (`FULFILLED` with `fulfilledByCapabilityId`, the "Inherited via <Capability>" note and `assessedAt` when a Capability the System declares is mapped to the Control, otherwise `NOT_STARTED`). The rows are built **before** the transaction and written by the same `createMany` as the recompute (`diffApplicabilityOpsWithCapabilities` for the single-System paths, the batched transaction for the catalog path), so a System is never half-applied. Only newly created rows are fulfilled; a recompute never updates an existing row, so a touched Assessment (or any existing one) can't be overwritten. When several declared Capabilities cover the same Control, the one credited is the first by name (code-unit order), then by id (`pickCapability`; `applyCapabilityRemoved` re-attributes by the same rule). Each Capability that fulfilled something gets a `"system"`-actor `ASSESSMENT_STATUS_CHANGED` Change Event worded like the declare path (`N Control Assessment(s) auto-fulfilled via Capability "X"`), in the same transaction on the catalog path and right after the person's own event on the classification and Framework Scope paths. The catalog path reads each System's declared Capabilities with the Systems and loads the Control to Capability mappings once per run, so it adds a constant number of queries (about 5) however many Systems are affected, and none when no affected System declares a Capability. Changing which Capabilities a Control maps to (the Control Library) still re-fulfils nothing on existing rows. Tests: `src/app/api/systems/__tests__/capability-fulfilment-recompute.test.ts`
- Admin CRUD (including retire) for the Deployment Facet, Capability, Business Unit, and Framework catalogs
- Control Owner (#119, PRD 0001 F-CL.3): every Control can have one **Control Owner**, a User of any role, who maintains the Control's Organization Control Implementation (#120). `Control.ownerId` is nullable (relation to `User`, `onDelete: SetNull`, indexed; hand-written migration `20261001100000_add_control_owner`, which only adds the column, the index and the foreign key), so every existing Control starts unassigned (PRD §9.7) and deleting a User who owns Controls leaves them unassigned. A Compliance Manager or an Admin assigns, replaces or clears it with `PATCH /api/controls/[id]` (`ownerId`: a User id, or `null` to clear; an unknown User id is a 400 and changes nothing; every other role gets 403); `POST /api/controls` takes no owner (create the Control, then assign). To fill that picker, `GET /api/users` now also lists Users for the roles that manage the requirement database (`COMPLIANCE_MANAGER`, besides `ADMIN`), in the same `PublicUser` shape; every other role still gets 404 outside the dev stub. Publishing a Framework is **not** blocked by Controls without a Control Owner (product-owner decision on #119). Tests: `src/app/api/controls/[id]/__tests__/control-owner.test.ts`, `src/app/api/users/__tests__/route.test.ts`, `src/components/__tests__/ControlLibraryManager.test.tsx`
- Full Control authoring: create a new Control Library entry (code, title, description, category, mandatory flag, applicability, Self-Assessment Question/intent/examples) and edit any of it later, from the admin UI — not just the facet/capability scoping. Which Frameworks a Control serves is expressed only through Control Mappings ("implement once, satisfy many", ADR 0005), never by tagging the Control directly. The admin list view surfaces every Control's Satisfies set (derived from its mappings) and tags (Deployment Facets, Impact Level thresholds) at a glance, to spot near-duplicates before creating a new row instead of tagging an existing one
- Framework Scope drives applicability (#85, [ADR 0007](docs/adr/0007-framework-scope-drives-applicability.md), PRD 0001 F-AP.1, F-FW.3, F-AP.3 partial): a Per-System/Both Control now applies to a System only if it's mapped, at any Coverage, to a Requirement of a **Published** Framework in the System's *effective Framework Scope* (its declared scope rows, plus the **base Framework (ISO/IEC 27001), which is always in scope**, whether or not a row is stored), on top of its existing Deployment Facet and Impact Level scoping. This is one DB-side filter in `getApplicableControls`/`getApplicableControl`/`getUnaddressedMandatoryControls` (`src/lib/control-assessments.ts`); `SystemClassification` gained a required `frameworkScopes: { id }[]`, loaded by `SYSTEM_SUMMARY_INCLUDE`. A scope row pointing at a Draft Framework is inert until it's published. A Control mapped to no Published Framework in scope applies to nothing (`scripts/check-unmapped-controls.ts` is a read-only report of Per-System/Both Controls with no Published mapping; it finds none on the seeded catalog). Declaring or removing a Framework Scope (`applyFrameworkScopeDeclared`/`applyFrameworkScopeRemoved` in `src/lib/framework-scope.ts`) recomputes the System's Assessments in one transaction through `diffApplicabilityOps` (new: Not Started; no longer applicable and untouched: removed; touched: kept as stale) and logs a Change Event with `+added/-removed` counts. The base Framework can't be removed (`DELETE` returns 409) and the System page lists it as fixed; `GET .../framework-scopes` always includes it (`isBase`). Framework Scope changes were Draft-only until #86 lifted the lock (see the continuous-compliance bullet). Tests that need a base Framework get one from `vitest.global-setup.ts` (the seeded one, or one created for the run on CI's unseeded DB) and map fixture Controls to it with `src/test/framework-fixtures.ts`.
- Recompute on requirement-database changes (#87, [ADR 0006](docs/adr/0006-continuous-compliance-replaces-draft-lock.md)/[0007](docs/adr/0007-framework-scope-drives-applicability.md), PRD 0001 F-AP.3, F-FW.5, F-CL.7): changes to the catalog now reach the Systems they affect, not only changes to a System's own classification. Triggers (each synchronous, inside the request): **publishing a Framework** (`onFrameworkPublished`; Systems with it in their declared scope), **adding or removing a Control Mapping on a Published Framework** (`POST`/`DELETE …/mappings`, a **Requirement deleted** on a Published Framework, and a **Supplementary Control created from a gap**; Systems with the Framework in scope, every System for the base Framework), and **editing a Control's scoping** (`PATCH /api/controls/[id]`: Deployment Facets or an Impact Level threshold, and only when the value actually changes; Systems with any Published Framework the Control maps to in scope). Not triggers: anything on a Draft Framework (inert until published), a Coverage-only mapping change (the gate is "mapped at any Coverage"), `mandatory`/text/Capability edits, and creating a Requirement (it carries no mappings). There is no unpublish and the base can't move (both refused by the Framework routes), so those are not triggers either. The shared logic is `src/lib/applicability-recompute.ts`: it compares each affected System's current Assessment rows with a freshly computed applicable set, restricted to the Controls the change touched, so it only ever creates `NOT_STARTED` rows for newly applicable Controls, removes untouched ones (the same definition as `diffApplicabilityOps`: `NOT_STARTED` and never assessed) and keeps touched ones as stale; it never writes `System.status`, `onboardedAt` or Approvals (F-AP.4). Systems that share a classification share one applicability query, and writes go in batches of 50 Systems per transaction. Every System whose applicable set changed gets a `"system"`-actor Change Event with the new action `APPLICABILITY_RECOMPUTED` (kept apart from `CLASSIFICATION_CHANGED`, which is the owner changing the System's own classification), detail e.g. `Applicability recomputed, Control Mapping removed: ISO/IEC 27001:2022 A.8.24 ↔ A.8.24 (+0/-1 Control Assessment(s), 1 kept as stale)`; Systems whose set didn't change get none. Since #110 the recompute also runs Capability auto-fulfilment for the Controls it creates (see the Capability bullet below). Measured on a 500-System scratch database: a base-Framework mapping change or a broad Control scoping edit took about 0.5-0.8 s when Systems share ~25 distinct classifications and 2.4-3.4 s in the worst case of every System having a unique classification, so it stays synchronous (no `after()`). Tests: `src/app/api/frameworks/__tests__/recompute.test.ts`
- Regulatory Overlay is retired (#88, [ADR 0007](docs/adr/0007-framework-scope-drives-applicability.md), PRD 0001 F-AP.6 and §9 step 4): "this System is subject to GDPR" and "GDPR is in this System's Framework Scope" are now the same statement. The overlay catalog (`/admin/regulatory-overlays`, `/api/regulatory-overlays/**`), the System declare/remove endpoints and widget, the overlay axis of `getApplicableControls`, the Control Library overlay picker, `regulatoryOverlayIds` on `PATCH /api/controls/[id]` and the `RegulatoryOverlay` model are gone. The hand-written migration `20260930100000_retire_regulatory_overlay` creates, for every overlay, a Framework of the same name (version `1`, licensing `QUOTABLE`, **Published**, not base; an existing Framework with that name and version is reused) and adds it to the Framework Scope of every System that declared the overlay, then drops the overlay tables. It writes no Requirements, Control Mappings, Assessments or Change Events, so every System's applicable-Control set and every Control Assessment are unchanged. Because the Framework gate is an OR across Frameworks in scope and cannot express "base AND overlay", it **aborts** (`RAISE EXCEPTION`, nothing changed) rather than silently widen a Control that is scoped to an overlay *and* mapped to a Published Framework (it would start applying to every System), and likewise when reusing an existing Published Framework that has mapped Controls would give declaring Systems new ones; an overlay-scoped Control mapped to no Published Framework applies to nothing before and after and gets no mapping (its overlay tag is dropped). `scripts/check-overlay-migration.ts` (read-only, `npx tsx scripts/check-overlay-migration.ts`, exit 1 when the migration would abort) reports the same plus a dry-run summary of the Frameworks, scope rows and Controls per overlay; run it against a database before deploying. The demo seed (`prisma/seed-demo-systems.ts`) now seeds the GDPR and EAR/ITAR Frameworks and scope rows so a seeded database matches a migrated one. The dev database had two overlays (GDPR on 3 Systems, EAR/ITAR on 1) and no overlay-scoped Controls.
- Organization Control Implementation (#120, PRD 0001 F-IN.1, migration §9.7): the Organization's own status and description for every **Organizational** and **Both** Control (Per-System Controls have none). Model `OrganizationControlImplementation` (`controlId` unique, `onDelete: Cascade`; `status` is the Control Assessment status set, default Not Started; `description`; `updatedById` with `onDelete: SetNull`; `updatedAt`). The hand-written migration `20261001110000_add_organization_control_implementation` creates the table and inserts a Not Started row for every existing Organizational/Both Control (data-driven, `ON CONFLICT DO NOTHING`, a no-op on an empty database; 92 rows on the seeded dev DB, 61 Organizational + 31 Both, none for the 26 Per-System Controls). New Controls get their row too: `POST /api/controls`, the supplementary-control route and the seed all call `createOrganizationImplementationFor` (`src/lib/organization-implementation.ts`). **A missing row reads as Not Started** (test fixtures and any Control created elsewhere have none), and the first edit creates it. "Who may edit" is one pure function, `canEditOrganizationImplementation` (`src/lib/organization-implementation-rules.ts`): the Control's Control Owner (whatever their role, a Viewer included), a Compliance Manager or an Admin; everyone else gets 403 and nothing is written. Setting the status to Waived or Not Applicable needs a non-empty description (400 otherwise; one named constant, `IMPLEMENTATION_STATUSES_REQUIRING_DESCRIPTION`; confirmed by the product owner). API: `GET /api/organization/controls` (every signed-in role: code, title, applicability, Control Owner, and the implementation with who updated it and when) and `PATCH /api/organization/controls/[controlId]` (`{ status?, description? }`; 404 for an unknown or Per-System Control, then 403, then 400). It writes no Change Event (`updatedById` and `updatedAt` are the record) and changes nothing on any System: applicability, Control Assessments, derived Requirement status and Compliance Percentage are untouched (inheritance is #121). Page `/organization/controls` ("Organization Control Implementations", readable by every role): a table with a status filter and an "Only Controls I own" filter, and an inline editor (status and description) on the rows the user may edit. `/home`: an "Organization Controls" tile for Compliance Manager and Admin, and Control Owner tasks for any role, a Compliance Manager included: one "My tasks" row per Control the user owns whose implementation is Not Started or In Progress (`src/lib/control-owner-tasks.ts`), linking to `/organization/controls?mine=1`. Tests: `src/lib/__tests__/organization-implementation-rules.test.ts`, `src/app/api/organization/controls/__tests__/route.test.ts`, `src/app/api/organization/controls/[controlId]/__tests__/route.test.ts`, `src/app/api/controls/__tests__/organization-implementation.test.ts`, `src/lib/__tests__/control-owner-tasks.test.ts`, `src/components/__tests__/OrganizationControlImplementations.test.tsx`
- Derived Requirement status per System, with a per-Framework view (#89, PRD 0001 F-AS.3, F-OUT.2 minimal, OQ-1): a Requirement is never assessed directly; its status for a System is derived live from the Control Assessments of its mapped Controls that apply to that System (`src/lib/requirement-status.ts`, pure rules in `requirement-status-rules.ts`). **Met** = every applicable mapped Control is effectively Fulfilled *and* the Requirement is covered (a Full mapping applies) and not an accepted gap; **Partially Met** = some are, or all are but the Requirement is only Partially covered or is an accepted gap; **Not Met** = none are; **Not Applicable** = mappings exist but none of the mapped Controls applies to the System (so it leaves the Compliance Percentage denominator). A Requirement with no mapped Controls at all is **Not Met** (one flagged constant; an open product question). "Effectively Fulfilled" is one function: Fulfilled, or Waived / Not Applicable unless the Framework is `strictComplianceRequired` (M3 inheritance extends it there). `/systems/[id]` gets a "Requirements by Framework" section: each Published Framework in the System's effective Framework Scope (declared rows plus the base) collapsed by default with per-status counts, then a status filter, Requirements by section, the applicable Controls behind each and their Assessment status. `deriveFrameworkStatusesForSystems` derives many Systems x one Framework in a constant number of queries, for #90's Compliance Percentage. No schema change. On the seeded demo data, ISO/IEC 27001:2022 clauses 4-10 and the Annex A Requirements mapped only to Organizational Controls show as Not Applicable per System until M3 brings Organization Control Implementation.
- Requirement-based Compliance Percentage per Framework (#90, PRD 0001 F-AS.4, F-OUT.3): the figure is always for one Framework, **Met Requirements ÷ applicable Requirements** (every derived status except Not Applicable; Partially Met counts as not Met; null, shown as "—", when nothing is applicable), replacing the old count of resolved mandatory Control Assessments. `getComplianceForSystems(where, { frameworkId? })` (`src/lib/compliance.ts`) pools it across the matched Systems that have the Framework in their effective scope (total Met ÷ total applicable, never an average, so a System with more applicable Requirements weighs more) and returns each System's own figure (`met`, `applicable`, `percentage`) too. It uses the bulk derivation, so there are no per-System queries. **With no Framework filter the headline is the base Framework's percentage** (the UI says so); a `strictComplianceRequired` Framework doesn't count Waived / Not Applicable as fulfilled. Shown in three places: the System page (a percentage in each Framework's header in "Requirements by Framework"), the Business Risk Owner dashboard's compliance section (filterable by Framework), and the System Portfolio cards (the filtered Framework's percentage, else the base's). Because Organizational Requirements are Not Applicable per System until M3, every place shows the note "Organizational Requirements aren't counted yet". Visibility follows one definition of "Systems in scope of a Framework" (`systemsInScopeOf`, `src/lib/framework-scope.ts`): the base Framework means every System, any other Framework the Systems with a stored scope row. So a Business Risk Owner assigned the base Framework now sees every System, not only the ones with a stored base row. No schema change.
- The `BUSINESS_RISK_OWNER` role (#55): a System now also self-declares which Business Unit(s) consume it and which Framework(s)' audit/certification boundary it's in scope for ("Framework Scope"). Business Units stay a purely reporting dimension, editable at any lifecycle stage. Framework Scope started out reporting-only too, but since #85 it drives which Controls apply (see the bullet above) and, like the other classification axes, can change at any lifecycle stage since #86. A Business Risk Owner is assigned a portfolio of Business Unit(s) and/or Framework(s) (independent axes, admin-managed) and gets a scoped, read-only dashboard: a cross-System Risk queue, a compliance-percentage view (Requirements Met ÷ applicable for one Framework, the base Framework unless filtered, pooled per scope, not averaged; see the #90 bullet above; a Framework can require strict scoring via `strictComplianceRequired`), and a System Portfolio view (#62) — Systems in scope grouped into status-colored clusters by `OnboardingStatus`, each card showing name, vendor, compliance-%, and open-Risk-count, linking to the System's own detail page — see [ADR 0004](docs/adr/0004-framework-as-first-class-entity.md) for why `framework` was promoted from a free-text tag to a first-class catalog entity to support this
- A role-differentiated landing page at `/home` (#54, redesigned by #57): a `PageHead` (mono page-id, serif title, lede, a stat-strip of headline counts), a unified "My tasks" status-row table for anything needing that role's attention (Systems, Risks, and Assessment Queries all in one table; a System Owner's Systems appear for a Rejected Draft, stale Assessments, or, since #86, N Controls needing assessment on a non-Draft System, each row tagged by kind and toned by real severity/urgency), and a "Where to start" tile grid of pure navigation shortcuts. `ADMIN`, `COMPLIANCE_MANAGER` and `VIEWER` — whose data isn't task-shaped — get the stat-strip and tile grid only, no task table, unless they own a System (next sentence). **Owner tasks for any role (#98):** anyone who owns at least one System (`ownerId`, whatever their role; an `ADMIN`'s rights over every System don't count) gets that System-owner task set — Rejected Drafts, stale or needs-assessment Systems, and Assessment Queries awaiting their reply — *in addition to* their role's own tasks (owner rows first, each Query listed once), so a `VIEWER` who owns a System gets a "My tasks" table they wouldn't otherwise have, plus a "Your Systems needing attention" stat (and "Open questions" where the role has none of its own); a user who owns nothing sees exactly what they saw before, and a `COMPLIANCE_MANAGER` never gets owner tasks even when recorded as an owner. The logic is `getOwnerTasks` in `src/lib/owner-tasks.ts`, and `roleView` (the per-role views, now in `src/app/home/role-view.ts`) adds it to every role. `/systems` still accepts `?status=` and `?owner=me` query params so tiles can deep-link into a filtered view
- `/` (#59, restyled in #64 to match the isms sign-in page) is a dev-stub-gated sign-in page: a segmented tile per seeded user plus a "Sign in →" button that stays disabled until a tile is picked, shown only when no acting user is set yet (redirects straight to `/home` once one is); the app header (#65, following the isms header: logo mark and wordmark, acting-user chip; wordmark only on `/`) doubles as the mid-session `RoleSwitcher` when the dev stub is on, a keyboard-operable listbox in the sign-in tile style, and redirects to `/home` after every switch instead of refreshing the current page, so switching to a role that can't see the current page never dead-ends on a 404
- Assessment Queries (#56): a `REVIEWER`/`RISK_OWNER`/`ADMIN` can raise a lightweight, non-blocking question thread scoped to one Control Assessment — the System Owner (or another `REVIEWER`/`RISK_OWNER`/`ADMIN`) replies inline, and a `REVIEWER`/`RISK_OWNER`/`ADMIN` marks it resolved once satisfied (never the System Owner, and not necessarily the original asker). Doesn't touch the Assessment's status, gate Approval, or affect the submission check — purely a turn-aware unresolved-count badge, shown on the Control's own row, rolled up per System on `/systems`, and as a landing-page card per role
- A Change Event log (#58): a curated `ChangeEvent` table records System-lifecycle-relevant mutations — status transitions, Approval decisions, Risk/Control Assessment status changes, Assessment Query activity, and classification/Capability/Business Unit/Framework Scope declare-or-remove — each tagged with an `action`, a human-readable `detail`, and an actor (a User id, or the literal `"system"` for a side effect the backend computed, like a Capability auto-fulfilling an Assessment or a "No" answer auto-opening a Risk). Deliberately not a full audit trail — pure catalog-admin CRUD is out of scope. Not surfaced in the UI yet; this is the data source a future "Recent updates" feed on `/home` will read from

## Getting started

You need Node.js 24 (see `engines` in `package.json`), Docker (for the local Postgres) and npm.

```bash
cp .env.example .env
docker compose up -d db
npm install
npx prisma migrate dev
npx prisma db seed
npm run dev
```

App runs at http://localhost:3000, health check at `/api/health`.

## Seeding a Vercel deployment

The seed script (`prisma/seed.ts`) is meant to run **once, from your machine, against the production database** — not as part of Vercel's build step, since a build can re-run and you don't want the seed firing repeatedly against prod.

```bash
npm i -g vercel        # if you don't have the CLI yet
vercel link            # link this checkout to the Vercel project, once
npm run vercel:env:pull  # writes .env.production.local (gitignored)
npm run prisma:seed:prod
```

Make sure `prisma migrate deploy` has already been run against that same database first (the Vercel project's build command is `npx prisma migrate deploy && npm run build`, so every production deploy applies pending migrations automatically; you can also run it manually with the same `.env.production.local`). Check `prisma/seed.ts` before re-running it against a real environment — it upserts most rows, but confirm it won't create duplicate demo data if run twice.

## CI/CD

- **Node version:** CI, the CD deploy job and the Docker image all run Node 24, the same as production. The workflows read it from `engines.node` in `package.json`; the `Dockerfile` can't, so it carries a matching `node:24-alpine`.
- **`.github/workflows/ci.yml`** runs on every pull request and push to `main`: lint, typecheck, unit tests against a real Postgres service container, production build, and a Docker build check. `react-hooks/set-state-in-effect` is currently downgraded to `warn` in `eslint.config.mjs` (8 existing components fetch in effects) so lint can pass — tracked in #63. Nothing in GitHub *enforces* CI on merge (see below), so the CD gate is what actually protects production.
- **`.github/workflows/cd.yml`** runs after CI succeeds on `main`: builds and pushes the production image to GitHub Container Registry (`ghcr.io/<owner>/<repo>`), then a `deploy` job (gated by the `production` GitHub Environment) deploys that commit to Vercel with the Vercel CLI (`vercel deploy --prod`; Vercel builds remotely, so its project env vars like `DATABASE_URL` stay in Vercel). Vercel's own Git auto-deploy is disabled for `main` in `vercel.json` so production only ships from a green commit; other branches still get Vercel preview deployments. **Migrations run only in production:** the Vercel project's build command is `if [ "$VERCEL_ENV" = "production" ]; then npx prisma migrate deploy; fi && npm run build`, and `DATABASE_URL` is set for the Production environment only. So a preview builds without touching any database, and its pages have no database at runtime. Until 2026-09-30 previews did run `prisma migrate deploy` against the **production** database, because `DATABASE_URL` was shared with Preview; see the workflow doc. The Neon Vercel integration still creates a `preview/<git-branch>` Neon branch per preview. Neon's free plan caps a project at 10 branches and doesn't delete merged ones, so clear old `preview/*` branches in the Neon console from time to time. When the cap is hit, new previews fail with "Resource provisioning failed". Requires a `VERCEL_TOKEN` secret (the org/project IDs are in the workflow file).

### Repo settings

- Branch protection/rulesets aren't available on this private, free-plan repo, so a red CI run can't block a merge. Production is still safe: the `deploy` job only runs after CI succeeds. If the repo moves to GitHub Pro (or goes public), protect `main` and require the CI workflow plus PR review.
- Add a `production` GitHub Environment with required reviewers if deploys should be gated by human approval.
- Set the `VERCEL_TOKEN` secret (on the `production` environment or repo-wide) for the deploy step — do not commit it.
