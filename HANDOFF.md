**#87 (recompute affected Systems on catalog changes) is done.** Key pieces, for when this needs revisiting:

A `RecomputeScope` is `{ systemsWhere, controlIds }` (which Systems, which Controls the change touched). `prepareRecompute(scope, { snapshot })` optionally captures "which of these Controls apply to each System right now" **before** the write (narrowing triggers: mapping removed, Requirement deleted, Control scoping edited); `finishRecompute(pending, trigger)` runs after it. It compares each System's current Assessment rows with the freshly computed applicable set for those Controls only (so it also heals a System an earlier failed recompute missed): no row and applicable, create Not Started; row, not applicable and untouched (`UNTOUCHED_ASSESSMENT_WHERE` in `control-assessments.ts`, now also used by `diffApplicabilityOps`: `NOT_STARTED` and `assessedById` null), remove; touched, keep as stale. Everything is synchronous in the request; a failure after the catalog write returns 500 but the next trigger for the same Controls heals it.

**#88 (retire Regulatory Overlay, ADR 0007) is done.** Key pieces, for when this needs revisiting:
- Migration `20260930100000_retire_regulatory_overlay` (hand-written). For each overlay: a Framework with the overlay's name and description, version `'1'`, `QUOTABLE`, **Published**, not base (an existing Framework with that name and version is reused); then every System that declared the overlay gets the Framework in `_SystemFrameworkScope` (`ON CONFLICT DO NOTHING`); then `_ControlToRegulatoryOverlay`, `_RegulatoryOverlayToSystem` and `RegulatoryOverlay` are dropped. Data-driven, a no-op on an empty database, writes no Change Events or Assessments. Column semantics used: `_ControlToRegulatoryOverlay` A = Control, B = overlay; `_RegulatoryOverlayToSystem` A = overlay, B = System; `_SystemFrameworkScope` A = Framework, B = System.
- **The deviation from the issue text (supervisor decision): no placeholder Requirements or Control Mappings are created, and the migration can ABORT.** The issue's recipe would silently widen applicability: the Framework gate is an OR across Frameworks in scope, so "overlay X AND base" cannot be expressed. Case by case: (1) an overlay-scoped Control mapped to **no Published Framework** applies to nothing today (#85) and stays that way, so it gets no mapping (mapping it to the new Framework would make it start applying) and its overlay tag is dropped; (2) an overlay-scoped Control mapped to a **Published Framework** (today it applies only to Systems declaring its overlay, afterwards it would apply to every System) makes the migration `RAISE EXCEPTION`, listing the Control codes, with nothing changed; (3) a Control scoped to two overlays falls under (1) or (2); (4) a name+version collision reuses the Framework, but if that Framework is Published, non-base, has mapped Controls and a declaring System doesn't already scope it, the scope row would give that System new Controls, so that aborts too. Every overlay-scoped Control that could pass the gate for some System is mapped to a Published Framework, so (2) catches them all and the migration never creates Requirements. The same "abort rather than widen" rule is stated in the migration's header comment.
- **If it aborts in production:** Prisma records the migration as failed and every later `migrate deploy` (so CD) refuses to run until it is resolved. Fix the data (unmap the listed Controls from the Published Framework, or drop their overlay scoping, by hand), run `npx prisma migrate resolve --rolled-back 20260930100000_retire_regulatory_overlay`, and deploy again. Better: run `npx tsx scripts/check-overlay-migration.ts` (read-only; exits 1 when the migration would abort) against production **before** merging. It prints, per overlay, the Framework it would create or reuse, the declaring Systems and scope rows, and the overlay-scoped Controls in three groups (mapped to a Published Framework: abort; Draft only: migrated but loses its overlay restriction; no mapping: dropped tag). The dev database passes: two overlays (GDPR on 3 Systems, Export Control (EAR/ITAR) on 1), no overlay-scoped Controls, so it creates two empty Published Frameworks and 4 scope rows.
- Code removed: `/admin/regulatory-overlays`, `RegulatoryOverlayManager`, `/api/regulatory-overlays/**`, `/api/systems/[id]/regulatory-overlays/**`, `src/lib/system-overlays.ts`, `SystemRegulatoryOverlays` (and its section on `/systems/[id]`), the overlay axis in `APPLICABILITY_SCOPING`, `regulatoryOverlays` from `SystemClassification` and every `include`/select (`SYSTEM_SUMMARY_INCLUDE`, `compliance.ts`, `dashboard.ts`, `frameworks.ts`, `CLASSIFICATION_SELECT` and `classificationKey` in `applicability-recompute.ts`), `regulatoryOverlayIds` on `PATCH /api/controls/[id]` (an unknown key is now simply ignored by zod), the Control Library picker, the admin home tile and stat, and the overlay block of `prisma/cleanup-test-fixtures.ts`. `prisma/seed-demo-systems.ts` seeds the GDPR and Export Control (EAR/ITAR) Frameworks (version 1, `QUOTABLE`, Published) and puts them in the demo Systems' Framework Scope, so a seeded database matches a migrated one.

## Conventions and gotchas learned this session

- **The repo lives at `C:\dev\requirement`, outside OneDrive** (moved 2026-09-29). In the OneDrive-synced folder, first compiles took tens of seconds, transient 404/500s were routine and sync caused file-lock trouble, so keep it out of synced folders. Turbopack still compiles each route on its first request; if a page shows "Compiling…", `wait` and re-screenshot.
- **Transient network blips** on `prisma migrate deploy`/`gh` commands (`Can't reach database server`, `TLS handshake timeout`) have shown up a few times and were not real failures — retry once; verify the DB itself is fine with `docker exec requirement-db psql -U app -d requirement -c "SELECT 1;"` before assuming something's actually broken.
- **Docker Postgres**: container `requirement-db`, user `app`, db `requirement`, port 5432, already running throughout this session (`docker ps --filter name=requirement-db`).
- **Full `vitest run` takes ~5–10 minutes and can flake under load, including component tests.** Two distinct causes seen this session: (1) a known pre-existing DB test-isolation issue — some Control fixtures are unscoped (apply to every Deployment Facet), so concurrently-running test files can collide on cleanup with FK-constraint errors; (2) plain 5s test timeouts on `ControlLibraryManager.test.tsx`/`NewSystemForm.test.tsx` etc. under full-suite parallel worker contention on this machine — these use mocked `fetch`, no DB involved, so it's pure resource contention, not a logic issue. Either way: if a file fails only under the full suite and passes when re-run alone or in a small batch, that's this flake, not a regression — don't chase it as one.
- **Tests run against the same Postgres database as `npm run dev`** (`DATABASE_URL` in `.env` isn't test-specific). If a background test run gets killed mid-flight (e.g. superseded by a follow-up command before its `afterAll` cleanup runs), its fixture rows (`Test ...`, `test-...@example.com`, etc.) leak into the dev DB and show up in the app UI. Harmless but untidy — periodically `SELECT` for `code`/`name`/`email` LIKE `'Test %'`/`'test-%'` across `Control`/`DeploymentFacet`/`Capability`/`RegulatoryOverlay`/`User` and clean up if it's gotten noisy (done once this session).
- **Renaming a Prisma model where a required scalar FK needs to become a many-to-many relation** (exactly what #47 did to `SystemType`→`DeploymentFacet`): `prisma migrate dev`'s auto-diff cannot express this as a data-preserving change on its own. Hand-write the migration SQL instead — rename the table in place (preserves rows/ids), create the new join table, backfill it from the old FK column *before* dropping that column, and get the new join table's `A`/`B` column semantics right (Prisma names implicit m:n join tables `_<ModelAlphabeticallyFirst>To<ModelAlphabeticallySecond>`, so renaming a model can flip which side is `A` vs `B` — see `prisma/migrations/20260914175041_replace_system_type_with_deployment_facet/migration.sql` for the full worked example, including the rename-dance needed to swap column identity without moving data).
- **Test conventions**: route handlers are tested by importing and calling the exported `GET`/`POST`/`PATCH`/`DELETE` functions directly against a real Postgres (not mocked) — see any `__tests__/route.test.ts` for the `requestAs`/`ctxFor` helper pattern. Component tests use Testing Library with `vi.stubGlobal("fetch", ...)`.
- **Domain vocabulary**: `CONTEXT.md` is the glossary of record. Use its exact terms in code, tests, commits, and issues — don't drift to synonyms it explicitly avoids (see each entry's `_Avoid_` line).
- **Issue tracker**: GitHub Issues via the `gh` CLI; conventions are in `docs/agents/issue-tracker.md`. Since PRD 0001 the flow is the supervised one in `docs/agents/supervised-workflow.md`: a sub-agent implements on a branch, then the supervisor reviews it, opens the PR, and merges on green CI. "Closes #n" in the PR body closes the issue.
- **README currency rule** (from `CLAUDE.md`): update `README.md`'s Project status whenever a change lands that affects what it describes. Don't let it go stale — this was the standing instruction that prompted the #47 README update.
