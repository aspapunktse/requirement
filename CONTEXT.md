# Requirement & Risk (GRC)

Governance, risk, and compliance for the systems and cloud solutions an enterprise runs: a requirement database of Frameworks mapped onto one Control Library, with each System assessed against the Controls that apply to it — first at onboarding, then continuously for as long as it lives.

## Language

### Systems and classification

**System**:
A system or cloud solution the enterprise runs or is onboarding. Progresses through a single onboarding lifecycle per System record (no re-onboarding of the same System as a new entity), and stays assessable after it's Onboarded (see **Continuous Compliance**). Declares its classification — one or more Deployment Facets, an Impact Level on each of Confidentiality/Integrity/Availability, and its Framework Scope — and any number of Providers it depends on (#124; a dependency changes what the System inherits, not which Controls apply to it). All of these can change at any lifecycle stage; each classification change recomputes the System's applicable Controls (see [ADR 0006](docs/adr/0006-continuous-compliance-replaces-draft-lock.md), which supersedes the Draft-only lock from [ADR 0003](docs/adr/0003-multiselect-deployment-facets-plus-overlays.md)).
_Avoid_: Vendor, application, service (use System even when the thing being onboarded is a SaaS vendor or cloud service)

**System's owner** (the person `ownerId` names): whoever is recorded as the System's owner, whatever their role. The creator becomes the owner, and only a System Owner, Risk Owner or Admin may create a System (#91). Being a Risk Owner, Reviewer or Viewer doesn't stop someone owning a System, and having the System Owner role doesn't make someone the owner of a System they weren't recorded on. Every owner action (editing Control Assessments and answering Self-Assessment Questions, submitting for review, changing classification, declaring Business Units and Framework Scope, logging a Risk, marking Onboarded) is allowed for the System's owner or an Admin, and nobody else, except the role-based grants that aren't about ownership (a Risk Owner logs Risks on any System and waives; see **Control Assessment** and **Risk**). A Compliance Manager is read-only on Systems, so they can't act as owner even if recorded as one. **Changing the owner** (#233): the System's current owner or an Admin may hand a System to another owner, one at a time from the System page or several at once from the Systems list, at any Onboarding Status; the new owner must have a System-creating role (System Owner, Risk Owner or Admin), the same roles that may create a System. The change is all-or-nothing (if any selected System is one the acting user may not change, none changes) and records one `SYSTEM_OWNER_CHANGED` Change Event per System that changed owner; a System already owned by the chosen user is left as it is. Open Check-ups and Assessment Queries follow the new owner. This is the one owner rule; the other entries say "the System's owner" and mean this.

**Deployment Facet**:
An admin-curated classification a System declares one or more of (e.g. On-Premises Datacenter, Cloud IaaS/PaaS, SaaS). A Control can be scoped to a subset of Facets; it then applies only to Systems declaring at least one of them. A System spanning multiple deployment models simply declares more than one Facet — Hybrid is not its own catalog entry (see [ADR 0003](docs/adr/0003-multiselect-deployment-facets-plus-overlays.md)).
_Historical note_: this concept was called "System Type" (exactly one per System) before ADR 0003.

**Impact Level**:
An ordinal classification — Low, Moderate, High, or Critical, one shared scale — the System's owner self-declares independently on each of three axes: Confidentiality, Integrity, and Availability. A Control may set a minimum Impact Level threshold on any of the three axes (or none); it applies to a System only once that System's declared level on that axis meets or exceeds the threshold. A System that hasn't yet declared a level on an axis ("not classified") never meets a threshold on that axis. See [ADR 0003](docs/adr/0003-multiselect-deployment-facets-plus-overlays.md).

**Framework Scope**:
The set of Frameworks a System is subject to. The base Framework (ISO 27001) is always in scope for every System; every other Framework is declared. Drives applicability: a System's applicable Controls are those mapped to Requirements of Frameworks in its scope, further filtered by each Control's Deployment Facet and Impact Level scoping (see [ADR 0007](docs/adr/0007-framework-scope-drives-applicability.md)).
_Historical note_: was a reporting-only "audit boundary" relation before ADR 0007.

**Regulatory Overlay** _(retired)_:
Was a boolean flag a System declared (e.g. GDPR, EAR/ITAR) to pull in extra Requirements. Replaced by Framework Scope: GDPR, EAR/ITAR and the like are now Frameworks in their own right (see [ADR 0007](docs/adr/0007-framework-scope-drives-applicability.md)). Don't use "overlay" for anything new.

**Business Unit**:
An admin-curated catalog entry representing an organizational consumer (e.g. Finance, HR) that a System declares is using it. Purely a reporting/grouping dimension — declaring a Business Unit has no effect on a System's applicable Controls. A System may declare any number of Business Units. Declared/changed by the System's owner or an Admin.
_Avoid_: Consumer, department, used-by (informal phrasing during design; Business Unit is the canonical term)

### The requirement database

**Framework**:
A curated catalog entry for a compliance standard, law, or regulation (e.g. ISO 27001:2022, Cybersäkerhetslagen, GDPR, CSA CCM 4, CMMC), made up of its own **Requirements** — the standard's line items (see [ADR 0005](docs/adr/0005-split-requirement-and-control.md)). ISO 27001:2022 is the **base Framework**: its Annex A defines the base Control Library, and every other Framework is mapped onto that library, adding Supplementary Controls only where no base Control covers a Requirement. Each version of a standard is its own Framework (ISO 27001:2013 and ISO 27001:2022 are two), optionally linked by "supersedes"; a national law that transposes an EU directive (e.g. Cybersäkerhetslagen for NIS2) is modeled as the Framework, not the directive. Carries a `strictComplianceRequired` flag: some Frameworks only accept Fulfilled (no partial credit for Waived/Not Applicable) when computing compliance against them. Is either **Draft** (being authored or mapped — invisible to Systems) or **Published**; only a Published Framework can be in a System's Framework Scope or affect applicability, and Supplementary Controls authored for a Draft Framework reach Systems only when it's published.
_Avoid_: Standard, regulation, overlay (Framework covers all of them)
_Historical note_: previously a bare `Requirement.framework: String[]` free-text tag, promoted to a first-class catalog entity in [ADR 0004](docs/adr/0004-framework-as-first-class-entity.md).

**Requirement**:
One line item of a Framework — a clause, article, or control objective as the standard itself states it (e.g. ISO 27001 clause 6.1.2, ISO 27001 A.8.24, NIS2 Art. 21(2)(h), CCM CEK-03). Belongs to exactly one Framework. Never assessed directly: it is satisfied through the Controls mapped to it (see **Control Mapping**), and its status for a System is derived, live, from the effective statuses of the mapped Controls that *count for that System* — a Per-System or Both Control that applies to the System (its Control Assessment, inherited where it can be), and an Organizational Control whenever the Requirement's Framework is Published and in the System's effective scope (the Organization's own status, since it has no Control Assessment; Deployment Facets and Impact Levels don't apply to it) — **Met** (covered, and every such Control effectively fulfilled), **Partially Met** (some are; also when all are but the Requirement is only Partially covered or is an accepted gap, since acceptance is a library-level judgment, not evidence that the System meets it), **Not Met** (none are), or **Not Applicable** (it has mappings but none of the mapped Controls counts for the System: every one is a Per-System or Both Control that doesn't apply to it, or the Framework isn't in its scope; excluded from the Compliance Percentage). So a Requirement met only by Organizational Controls (ISO/IEC 27001 clauses 4–10 and most of Annex A) counts on every System that has its Framework in scope, as Not Met until the Organization implements the Controls (#122; the drop on the day it shipped was an accepted product-owner decision). "Covered" is judged over the mappings that count for the System. *(Glossary change flagged for the product owner: the "until M3" / "e.g. only Organizational Controls" Not Applicable wording is gone, and the rule above for which mapped Controls count is new, #122.)* A Requirement with no mapped Controls at all is **Not Met** (a provisional rule, so an unmapped Framework can't look compliant). Waived / Not Applicable statuses count as Fulfilled unless the Framework has `strictComplianceRequired`; this holds for an Organizational Control's implementation status too. For licensed standards the catalog holds only the identifier, title, and an own-words paraphrase, never verbatim text; public-domain texts (e.g. EU law) may be quoted.
_Avoid_: Clause, framework requirement (Requirement alone is the canonical term), Control (a different, organization-authored thing — see below)
_Historical note_: before [ADR 0005](docs/adr/0005-split-requirement-and-control.md), "Requirement" meant what is now called **Control**.

**Control**:
A reusable, organization-authored safeguard that satisfies one or more Requirements, potentially from several Frameworks at once ("implement once, satisfy many") — security, privacy, legal, or operational — independent of any specific System. Either a **base Control** (seeded 1:1 from ISO 27001:2022 Annex A) or a **Supplementary Control**. Carries an Applicability — Organizational, Per-System, or Both — and, for Per-System/Both Controls, optional Deployment Facet and Impact Level scoping (independently optional, composed with AND; empty/unset means "applies regardless"). An Organizational Control is implemented once by the Organization (see **Organization Control Implementation**) rather than assessed per System. A mandatory Control applicable to a System must have some Control Assessment recorded before that System can be submitted for review. Which Frameworks a Control serves is expressed only through Control Mappings, never by tagging the Control with Frameworks directly. Each Control has a Control Owner.
_Avoid_: Policy, measure, safeguard (Control is the canonical term)

**Supplementary Control**:
A Control added beyond the ISO 27001 Annex A base because some Framework's Requirement has no base Control covering it (e.g. "notify the national CSIRT of significant incidents within 24h" for Cybersäkerhetslagen). Records its **origin Framework**. Once it exists it is an ordinary Control — other Frameworks' Requirements can map to it too.
_Avoid_: Overlay, overlay control

**Control Library**:
The full set of Controls — base plus Supplementary — available to assess Systems against. Curated centrally, by Compliance Managers, to avoid drift or duplicate/inconsistent controls across Systems.
_Avoid_: Requirement Catalog (its name before [ADR 0005](docs/adr/0005-split-requirement-and-control.md)), Requirement database (the informal name for the whole Framework + Requirement + Control Library + mapping set)

**Control Mapping**:
A many-to-many link between one Requirement and one Control, carrying a **Coverage** of Full or Partial. A Requirement is **covered** when at least one of its mappings has Full coverage; several Partial mappings never add up to Full, so a Requirement with no mappings, or only Partial ones, is a **Coverage Gap** — the trigger for authoring a Supplementary Control (one action creates the Control with its origin Framework and a Full mapping to the Requirement). A Coverage Gap a Compliance Manager has accepted with a justification is an **accepted gap**: shown separately from open gaps, and counted as resolved for coverage metrics. Gaining a Full mapping ends an acceptance (the Requirement is covered).

**Statement of Applicability (SoA)**:
The organization-wide ISO 27001 statement listing every Control in the Control Library with whether it is included, the justification for including or excluding it, and its implementation status. Generated from applicability and assessment data, with exclusion justifications authored by a Compliance Manager.
_Historical note_: before this model, "SoA" was used loosely to mean a System's Framework Scope; it now carries only its proper ISO meaning.

### Implementing and inheriting Controls

**Organization**:
The enterprise itself, as the implementer of Organizational Controls. Single instance while the app is single-tenant.

**Organization Control Implementation**:
The Organization's own status and description of how it implements one Control (e.g. A.5.1 policies, A.6.1 screening). Maintained by that Control's Control Owner, or by a Compliance Manager or an Admin (PRD F-IN.1). For a **Both** Control it is inherited by every System the Control applies to, while it is Fulfilled (see **Control Inheritance**). For an **Organizational** Control it is the Control's status on every System that has the Control's Framework in scope, whatever it is (Waived and Not Applicable count except on a strict Framework; see **Requirement**): nothing is inherited, because no System assesses the Control. A Control with no recorded implementation reads as Not Started. A change to an Organizational Control's status is a System-less Change Event. *(Glossary change flagged for the product owner: "inherited by every System" is now qualified by Both and by Fulfilled, #121; the Organizational paragraph is new, #122.)*

**Provider**:
A System that other Systems depend on and inherit Controls from (e.g. a landing zone, a directory service, a central KMS). Publishes Control Offerings. Its offerings count only once the Provider itself is Onboarded. A System declares which Providers it depends on (see [ADR 0008](docs/adr/0008-providers-are-systems.md)). The System's owner or an Admin marks a System as a Provider, at any lifecycle stage, and unmarking is refused while it has Offerings (#123) or while any System depends on it (#124). A System can only depend on a System marked as a Provider, never on itself; its owner or an Admin declares and removes the dependency at any lifecycle stage of either System (a Compliance Manager never), and each is a Change Event on the dependent like a Framework Scope change. Mutual dependencies are allowed, because nothing is inherited through a chain: a dependent reads the Provider's **own** Assessment status of the Control, never what the Provider itself inherits from the Organization or from its own Providers. **What someone who can't see a Provider as a System may learn about it:** its name, whether it is Onboarded, its Control Offerings and its own Assessment status for each offered Control, nothing else (no owner, classification, description, evidence or notes); the owner of any System can pick any Provider. *(Glossary change flagged for the product owner: the dependency rules, the no-chain rule and the visibility rule are new wording here, #124.)*
_Avoid_: Capability (the retired, non-System predecessor), platform, shared service

**Control Offering**:
A Provider's statement that it implements one Control for the Systems depending on it, with an inheritance type of **Full** or **Shared** and, for Shared, a **customer responsibility** text describing what the depending System must still do itself (a Full Offering has none). The System's owner or an Admin maintains a Provider's Offerings. A Provider can only offer a Control that **applies to it**, so it has a Control Assessment for it, and that Assessment's own status (never the Provider's effective status) is what dependents read (#124). If the Control later stops applying to the Provider (a classification or catalog change), the Offering is **kept**, never deleted by a recompute, and is reported as no longer applying; it can still be edited or removed, and it gives no credit. A Full Offering gives the Systems depending on the Provider credit only while the Provider is **Onboarded** (before that it is shown as *pending: Provider not Onboarded*), the Control still applies to the Provider and the Provider's own status is Fulfilled; a **Shared** Offering covers only the Provider's half: it is listed on the dependent with its customer responsibility (also next to the status field of the dependent's Assessment form), and gives credit only together with the dependent's own half, see **Control Inheritance** (#125). *(Glossary change flagged for the product owner: the applies-to-the-Provider rule and the kept-Offering rule are new wording here, #123; what a Shared Offering gives is new, #125.)*

**Control Inheritance**:
A System satisfying a Control through someone else's implementation of it rather than its own — from the Organization (an Organization Control Implementation) or from a Provider (a Control Offering). **Full** inheritance covers the Control entirely; **Shared** inheritance still requires the System to address the customer responsibility itself: the System's own Control Assessment is **the customer's half** and the Provider's Offering is the Provider's half (#125). Inherited status is **live**: it always reflects the source's current status, never a copy taken at declaration time. A System's own Control Assessment can override an inherited one, and the System's owner or an Admin can **reset** it to inherited (see **Control Assessment**). A Control not inherited at all is **System-specific**.
What a System is judged by is a Control's **effective status**, resolved live and never stored: (1) the System's own Control Assessment if a person set one (`assessedById` is not null), whatever it says, except that an own **Fulfilled** next to a Shared source is only the customer's half (see below); (2) otherwise a Full source whose status is Fulfilled makes it Fulfilled; (3) otherwise the System's own status (an Assessment nobody set, or none at all, counts as Not Started). **Only a Fulfilled source is inherited**: an Organization Control Implementation that is In Progress, Not Started, Waived or Not Applicable gives no credit, and the System's own status stands (product-owner decision on #121). The sources are the Organization (only for **Both** Controls) and, since #124, the Control Offerings of the Providers the System depends on (for a **Per-System** or a **Both** Control): a Provider source's own half is satisfied only while the Provider is Onboarded, the Control still applies to it and its own status is Fulfilled, and a **Full** Offering gives credit on that alone, shown as *Inherited from Provider X: Full*. A **Shared** Offering also needs the System's own half: the own Assessment is Fulfilled (whoever set it, so a Fulfilled Assessment nobody set counts too), and then the Control is Fulfilled, shown as *Inherited from Provider X: Shared*. The System's own Waived or Not Applicable still wins outright, and a person-set In Progress or Not Started is the effective status. An untouched own Assessment with only Shared sources stays Not Started: the customer's half is not done, which is a task for the owner. When the own Assessment is Fulfilled but no Shared source's Provider half is satisfied and no Full source gives credit, the Control is effectively **In Progress**: not Met, it passes the submission check and it is not a "needs assessment" task for the owner (the Provider's half is what is missing, and the System page says why: the Provider is not Fulfilled, not Onboarded or the Control no longer applies to it). Declaring a dependency on a Provider with a Shared Offering can therefore lower a System that had Fulfilled the Control itself; a `"system"` Change Event records it. With several sources for one Control the **most favourable wins** and **every source is listed** (OQ-2): since only Fulfilled gives credit, a Control is effectively Fulfilled if any source gives credit (one satisfied Shared source is enough, and a Full source that gives credit makes it Fulfilled whatever the own Assessment is); the sources are listed in a fixed order (the Organization, then Providers by name and then id). An **Organizational** Control is not inherited either: it has no Control Assessment, so its effective status for a System is simply the Organization's implementation status ("Implemented by the Organization"), judged like an Assessment status, which is deliberately more generous than the Both rule above (Waived and Not Applicable count, #122). Inheritance copies nothing: the System's Control Assessment keeps its own status, and every reader that judges compliance or completeness (derived Requirement status, the Compliance Percentage, the submission check, the "needs assessment" count, the System page) uses the effective status. When an implementation's status moves a System's effective status, that System gets a `"system"` Change Event. A person-set Assessment overrides every source until it is **reset to inherited** (#129): the System's owner or an Admin can return the System's own Assessment of a Control that has at least one **Full** inheritance source for that System (the Organization for a Both Control, or a Full Offering) to untouched, whatever the source's current status is, so the effective status is again whatever the sources give. A Control with no Full source (a Per-System Control of a System that depends on no Provider offering it, or one only a Shared Offering covers: its own Assessment is the customer's half, so there is nothing to go back to) or an Assessment nobody set has nothing to reset; the existence of a Full source is enough, also a pending one. When a **Provider's** own status, Onboarded status, Offering or dependency changes (#124), each dependent whose effective status for a Control actually moved gets a `"system"` Change Event (`A.8.24 is now Fulfilled, inherited from Provider "Landing Zone"`, `... (Shared)` for a Shared Offering, or `A.8.24 is now In Progress: waiting for Provider "Landing Zone" to provide its half`), written in the same transaction as the change; the others get none. The dependent's own edit is its own Change Event, which also says what the Control effectively is when that differs from the status stored (for example Fulfilled held at In Progress). *(Glossary change flagged for the product owner: the effective-status rules, "only Fulfilled is inherited" and the Change Event are new wording here, #121; the reset is new, #129; the Provider sources, the most-favourable-source rule and the Provider fan-out are new, #124; Shared inheritance, the customer's half, the In Progress case and the Full-source-only reset are new, #125.)*

**Capability** _(retired)_:
Was a standalone, non-System catalog entry (e.g. Active Directory) whose declaration auto-fulfilled mapped Requirements. Replaced by Provider (see [ADR 0008](docs/adr/0008-providers-are-systems.md)).
Each Capability that existed was migrated to a Provider System (#126): created Onboarded and owned by an Admin, classified as the union of the Systems that declared it, with a Full Offering for each Control it mapped that applies to it (backed by a Fulfilled Assessment noted "migrated from Capability — verify"), and with every System that declared the Capability depending on it. Nothing is fulfilled by copying a status any more: a dependent inherits live (see **Control Inheritance**). *(Glossary change flagged for the product owner: the "until that replacement lands" paragraph is gone, and this migration sentence is new, #126.)*

### Assessing

**Control Assessment**:
The fulfillment status of one Control for one specific System (Not Started, In Progress, Fulfilled, Not Applicable, Waived). This is where "does this System implement this Control?" is answered — neither the Control nor any Requirement carries a status of its own; Requirement status for a System is derived from these. Waiving or marking Not Applicable a mandatory Control requires a justification note and is restricted to Risk Owners/Admins — a user holding the System Owner role cannot wave off their own mandatory Control, and a Risk Owner who *owns the System* cannot waive or mark Not Applicable (or answer N/A to the Self-Assessment Question of) one of its **mandatory** Controls either: another Risk Owner or an Admin has to (#97; the API answers 403, and the UI hides those options). An owning Risk Owner may still waive its non-mandatory Controls, and an Admin may waive anything, including on a System they own. Only the System's owner or an Admin may otherwise edit an Assessment or answer its Self-Assessment Question (and submit the System for review); a Risk Owner who isn't the owner may only do the waive/Not Applicable transitions, changing the status and the justification note but never the evidence (the API rejects an evidence change from such a user with 400, #91), and no other role — Reviewer, Viewer, Business Risk Owner, Compliance Manager — may edit at all (#78). Where a Control is inherited, the Assessment shows its source (*System-specific*, or *Inherited from Organization* with the Organization's own status; later e.g. "inherited from Azure Landing Zone — Shared") and stays overridable: a System's own Assessment that a person set always wins, while one nobody set (or no row at all) is effectively Fulfilled for as long as the source is. The stored status is the System's own and is never changed by inheritance. *(Glossary change flagged for the product owner: the "person-set wins, untouched is inherited" sentence is new, #121.)*
The way back from a person-set Assessment to inheriting is a **reset to inherited** (#129): the System's owner or an Admin (a Compliance Manager stays read-only, everyone else gets 403) can return the System's own Assessment of a Control that has a **Full** inheritance source for that System (the Organization, or a Full Provider Offering; a Shared Offering doesn't count, #125) to untouched, meaning Not Started, nobody recorded as the assessor, and no evidence, notes or Self-Assessment answer, so it is effectively whatever the sources give again (Fulfilled while the Organization is, else Not Started and a task again). It is allowed whatever the source's status is, and refused (409) for a Control with no Full source, a stale Assessment, or an Assessment nobody set. The cleared status, evidence, notes and Self-Assessment answer are first recorded in a Change Event (`ASSESSMENT_STATUS_CHANGED`, attributed to the User who reset it), so the record survives in the log; the row, its Assessment Queries and the Risks linked to it stay as they are. *(Glossary change flagged for the product owner: the reset to inherited and the Change Event that records it are new wording here, #129.)*
An Assessment whose Control no longer applies to the System but which someone already worked on is kept as **stale** (shown under "No Longer Applicable" and counted in the owner's "My tasks") rather than deleted. The System's owner or an Admin can **remove** a stale Assessment (#109; a Compliance Manager stays read-only, everyone else gets 403): its last status, evidence and notes are first recorded in a Change Event (`ASSESSMENT_REMOVED`), so the record survives in the log. Removal is refused (409) while the Control still applies, and while an Assessment Query on it is still open. *(Glossary change flagged for the product owner: removing a stale Assessment, and the Change Event that records it, are new wording here.)*
_Historical note_: called Requirement Assessment before [ADR 0005](docs/adr/0005-split-requirement-and-control.md).

**Self-Assessment Question**:
The question posed to the System's owner for one Per-System/Both Control, answered Yes, No, or N/A. Yes sets the Control Assessment to Fulfilled; No leaves the Assessment open and automatically creates a Risk linked back to it; N/A sets the Assessment to Not Applicable, still subject to the justification/Waiver rule for mandatory Controls.

**Assessment Query**:
A lightweight, non-blocking question/reply thread a Reviewer, Risk Owner, or Admin raises against one specific Control Assessment (as does a **Review Group** member of any role, a Compliance Manager included, but only on Assessments of Controls in the group's remit on that System, and never on a System they own), without rejecting the whole System (see #56). Purely informational: it never changes the Assessment's status, gates an Approval decision, or affects the mandatory-Control submission check. Made up of one or more **Query Messages** and an explicit `resolved` flag set only by a Reviewer/Risk Owner/Admin or such a member (never someone acting only as the System Owner, and not necessarily whoever raised it). A message, and who resolved the thread, is attributed when it is posted: to the member's group, or "Base review" for a Reviewer, with the same rule for who sees the person as a Review Step's decision; an Admin's stay named, and so do a Risk Owner's unless the Risk Owner is a member posting on a Control in their group's remit, where membership wins and it shows as the group; a later change of membership never rewrites an old thread. Posting a new Query Message on an already-resolved thread reopens it automatically. More than one Assessment Query can be open on the same Assessment at once. Visible to anyone who can already see the System.
_Avoid_: Question (that term means **Self-Assessment Question**), Comment (that's `Approval.comment`)
_Historical note_: called Requirement Query before [ADR 0005](docs/adr/0005-split-requirement-and-control.md).

**Internal Audit**:
An engagement run by an Internal Auditor to verify that one or more Controls actually work, across a selection of Systems (by filter or by hand) and/or the Organization's own implementations. Generates one Check-up per recipient per Control, all sharing the Internal Audit's due date. An Internal Auditor **closes** a launched audit once every Check-up is evaluated or withdrawn (refused, naming the open ones, while any is not); a closed audit and its Check-ups, responses, evaluations and withdrawals are read-only for every role, the Internal Auditor included, though a Risk a Nonconformity opened stays an ordinary Risk (#158). A draft is deleted, not closed. Ad-hoc only for now; recurring schedules are future work.
_Avoid_: Audit (alone — ambiguous with external certification audits and with Change Event's explicitly-not-an-audit-log scope), campaign, review (Approval's territory)

**Check-up**:
One Control-verification request within an Internal Audit, sent to the System Owner (for a System's Control Assessment) or the Control Owner (for an Organization Control Implementation). Its question defaults to the Control's Self-Assessment Question and can be edited or extended by the auditor. The recipient answers Yes/No/N/A with a free-text description and evidence links; the answer itself never changes any status. An Internal Auditor can instead **withdraw** a Check-up that isn't evaluated, with a required reason: a withdrawal is final, takes it out of the recipient's tasks, bars answering and evaluating it, and keeps any response as part of the record; it writes no Change Event (#158). The Internal Auditor otherwise evaluates it as **Conforming**, **Observation**, or **Nonconformity**. A Nonconformity automatically opens a Risk linked to the Check-up (on the System for a System-level Check-up; one System-less **Organization Risk** for an Organization-level one) and, only if the targeted Control Assessment (or Organization Control Implementation — which then flows live to every inheriting System) is stored as Fulfilled, sets it back to In Progress, attributed to `"system"`, with a note linking to the finding; any other status is left as it is. A System-level set-back keeps the Assessment person-set, so the System stays effectively In Progress instead of falling back to a Fulfilled inheritance source; a System that is Fulfilled only through inheritance (no row, or a row nobody set) gets its own person-set In Progress status written, overriding the source (#157; see [ADR 0009](docs/adr/0009-a-risk-can-belong-to-the-organization.md)).
_Avoid_: Assessment Query (a non-blocking reviewer thread with no formal outcome), Self-Assessment Question (the catalog-authored question a Check-up merely defaults to)

**Continuous Compliance**:
The principle that a System's Control Assessments stay live after onboarding. A change to its classification, Framework Scope, or Providers — or a new Framework or Control reaching it — recomputes its applicable Controls: newly applicable ones get Not Started Assessments, no-longer-applicable untouched ones are removed, and no-longer-applicable touched ones are kept as stale for the owner to resolve (by editing it, or by removing it once no Assessment Query on it is open, #109). This never reopens the onboarding Approval or changes the System's status; the newly Not Started Controls (and any stale Assessments) show up in the owner's "My tasks" and in compliance figures. See [ADR 0006](docs/adr/0006-continuous-compliance-replaces-draft-lock.md).

**Compliance Percentage**:
Always for one Framework: the proportion of that Framework's applicable Requirements that are Met, where applicable means every derived status except Not Applicable, and Partially Met counts as not Met. For a given scope (a Business Unit, a Framework, or both combined) it is pooled across every System in that scope that has the Framework in its effective scope (total Met ÷ total applicable, not an average of each System's own percentage), so a System with more applicable Requirements weighs more. A System's own percentage is also shown standalone (on the System page per Framework, and on the Business Risk Owner's portfolio cards). Null, shown as "—", when nothing is applicable. With no Framework filter the headline figure is the **base Framework's**, and the UI says so. A Framework with `strictComplianceRequired` set treats Waived/Not Applicable Control Assessments as not Fulfilled when deriving Met. Requirements satisfied only by Organizational Controls are counted on every System that has the Framework in scope (#122; for ISO/IEC 27001 that is the 61 clauses and Annex A Requirements mapped only to Organizational Controls), so the percentage stays low until the Organization records its implementations. *(Glossary change flagged for the product owner: the "until M3 / aren't counted yet" wording and the UI note are gone, #122.)* "Systems in scope of a Framework" means every System for the base Framework (always in scope), and the Systems with a stored Framework Scope row for any other.

### Risk, approval, and people

**Risk**:
A risk identified either ad-hoc (logged directly by the System's owner or any Risk Owner or Admin, matching no predefined Control) or automatically: generated when the System's owner answers a Control's Self-Assessment Question "No" (carrying a link back to the originating Control Assessment), or opened by an Internal Auditor's **Nonconformity** on a Check-up (carrying a link back to that Check-up; at most one Risk per Check-up, opened with Medium severity and likelihood and no owner, for the Risk Owner to adjust and assign, #157). All follow the same lifecycle. A Risk belongs to a System, with one exception: a Nonconformity on an **Organization-level** Check-up opens one **Organization Risk** that belongs to no System (it is not copied onto each inheriting System). A Risk Owner and an Admin see and manage an Organization Risk (status, mitigation plan, owner), and the Internal Auditor reads it and changes nothing. Nobody else sees it, and the Business Risk Owner's scoped views never list it, being per System. Every Risk has a System or a Check-up, never neither. See [ADR 0009](docs/adr/0009-a-risk-can-belong-to-the-organization.md).
_Avoid_: Issue, finding (when referring to a tracked Risk record specifically)

**Approval**:
A reviewer's recorded decision on one Review Step of a System's onboarding. Approval is a judgment call made by a human reviewer — it is not automatically derived from Control Assessment or Risk status. A reviewer may approve a System despite open gaps, at their discretion.

**Review Group**:
A named set of Users who review Systems on behalf of the Frameworks the group is tied to. Its remit on a System is the non-base Controls (in practice Supplementary Controls) that apply to the System through a Requirement of one of its Frameworks in the System's Framework Scope; base Controls always stay with the base Review Step, even when they also satisfy that Framework. A Framework is tied to at most one Review Group, and one Review Group may be tied to several Frameworks. A Framework with no Review Group adds no Review Step, and its non-base Controls fall to the base Review Step. Membership is independent of role (as with Control Owner), except that an Internal Auditor can't be a member. Being a member lets a User decide the group's Review Step, see every System (any status) that has one of the group's Frameworks in scope, and raise and resolve Assessment Queries on Assessments of Controls in the group's remit on that System. An Admin creates, renames and deletes Review Groups and manages their members; an Admin or a Compliance Manager ties a Review Group to a Framework. A Review Group can't be deleted while it is tied to any Framework; untying it, or removing its last member, never blocks anything (a tied group with no members keeps its Review Step, which then only an Admin can decide). Membership is maintained by hand for now. Later a Review Group is to be linked to one Entra ID group, which then supplies its membership; the Review Group itself (its name and Framework ties) stays the app's own record.
_Avoid_: Group (alone — too close to Business Unit and to Entra ID groups), review board, team

**Review Step**:
One of the parallel decisions a System In Review needs before it is Approved. There is always the **base Review Step**, decided by a Reviewer or an Admin and covering every base Control (plus the non-base Controls of Frameworks with no Review Group). There is also one step per Review Group that has at least one Control in its remit on the System; a System whose scope brings two Frameworks with the same group gets one step for that group. Any one member decides the group's step, and an Admin can decide any step; a Reviewer who isn't a member decides only the base step. Nobody decides a step on a System they own. Each decision needs a comment. Open steps show in the deciders' "My tasks". The steps are derived live from the System's current Framework Scope: if a group's remit disappears while the System is In Review, its step goes (even an approved one); a newly in-scope group gets an open step; decisions on the other steps stand, and a step that disappears and comes back during the same Review Round comes back open. An owner edit to an Assessment of a Control in a step's remit after that step approved reopens the step (an edit to a base Control reopens the base step). Being the Control Owner of a Control in the remit doesn't bar a member from deciding.
**A step decides as its group, not as a person.** Every step's decision and its comment are shown attributed to the group ("GDPR Review Group: Rejected: …", or "Base review: Approved" for the base step), on the System page, in the approval history and in the Recent updates feed. Who actually decided is always recorded, but only an Admin, an Internal Auditor or a Compliance Manager sees it, plus the members of that group for a group's step and Reviewers for the base step. Everyone else, the System's owner included, sees only the group. The same holds for Query Messages posted by a Review Group member (shown as the group) and by a Reviewer (shown as "Base review"). An Admin's Query Messages stay named, and so do a Risk Owner's (a Risk Owner decides no step), unless the Risk Owner is a member posting on a Control in their group's remit: there membership wins and the message shows as the group.

**Review Round**:
One submission of a System for review, from the moment the owner submits it until every Review Step has approved or one has rejected. Every Approval belongs to exactly one Review Round, and a resubmission starts a new one, so earlier rounds' decisions never count toward the current one. The System's approval history is shown grouped by Review Round. Approvals recorded before Review Steps existed each sit in a Review Round of their own, as base Review Step decisions. The System becomes Approved only when every step has approved. If any step rejects, the System returns to Draft at once, the other open steps are cancelled, and on resubmission every step runs again. Review Steps exist only for onboarding: a Framework added to an Onboarded System brings no Review Step (see **Continuous Compliance**; a standalone Framework review of an Onboarded System is future work).

**Onboarding Lifecycle**:
The sequence a System moves through: Draft (owner is assembling assessments) → In Review (submitted by the owner; requires every applicable mandatory Control to have an Assessment) → Approved (every Review Step approved) or Rejected (any Review Step rejected) → Onboarded. Rejected returns to Draft for revision and resubmission rather than ending the System's record. Approved and Onboarded are distinct: Approved means a reviewer cleared the System to proceed; Onboarded means the actual technical integration/cutover has since been completed, a separate later event triggered by the System's owner or an Admin. Onboarding is a System's first assessment, not its last (see **Continuous Compliance**).

**Control Owner**:
The User accountable for one Control organization-wide. Maintains that Control's Organization Control Implementation. Assigned per Control by a Compliance Manager; any User can hold it, independent of role.

**Compliance Manager**:
A role that curates the requirement database — Frameworks, Requirements, the Control Library, and Control Mappings — assigns Control Owners, and authors Statement of Applicability justifications. Separate from Admin, who manages users, roles, and the remaining catalogs.

**Internal Auditor**:
A role that runs Internal Audits and evaluates Check-up responses. Reads everything; cannot edit Control Assessments, the requirement database, or Risks — independence from what it audits is the point (ISO 27001 clause 9.2). Admins and Compliance Managers can't evaluate Check-ups, since they'd be auditing their own work.

**Business Risk Owner**:
A role scoped to a portfolio of Business Unit(s) and/or Framework(s) it's assigned to (independently — may own Business Units, Frameworks, or both), rather than the full cross-System visibility `Risk Owner` has. Being assigned the base Framework means seeing every System, since the base is in every System's scope. Sees Risks (never an Organization Risk, which belongs to no System), Compliance Percentage, and a System Portfolio view (Systems in scope grouped by `OnboardingStatus`, each with its compliance-% and open-Risk-count) for Systems within its assigned scope only, filterable by Business Unit and Framework together. Read/reporting-only — does not manage Risk status. Can also drill into a System's own detail page for any System within its assigned scope, any status.
_Avoid_: Scoped Risk Owner (Business Risk Owner is the canonical term)

**App Setting**:
A value an Admin can change without a deploy, on the Admin-only Settings page (`/admin/settings`, #240). Each is declared once in code (key, label, section, whole-number range, default); a setting nobody has saved uses its default, so a change takes effect at once and nothing is stored until an Admin saves. Today's two belong to the Systems list: the age after which an untouched Draft needs attention (1 to 365 days, default 60) and the percentage the "Under N% met" view uses (1 to 100, default 70). Saving a value that differs from the one in force records one System-less `APP_SETTING_CHANGED` Change Event (key, old and new value); saving the same value changes nothing. The page shows who last changed each and when. Trend lines on the Systems list count earlier days under the value then in force, so a line can jump on the day a threshold changes.
_Avoid_: Config, Preference (a Preference would suggest a per-User choice; an App Setting is global)

**Change Event**:
A curated record of one compliance-relevant mutation, feeding the landing page's "Recent updates" feed (see #58). Either System-scoped — a status transition, a change of the System's owner (one event per System, naming the previous and new owner, #233), an Approval decision, a Risk status change, a Control Assessment status change (a reset to inherited included, #129) or the removal of a stale one, Assessment Query activity, or a classification/Provider/Business Unit/Framework Scope declare-or-remove (marking or unmarking a System as a Provider included, and declaring or removing a dependency on a Provider, #124), or a System created (`SYSTEM_CREATED`, by its creator, #245), or a Risk logged on a System (`RISK_LOGGED`, #245: by the person who logged it, or by `"system"` when a "No" Self-Assessment answer or an Internal Auditor's Nonconformity opened it; the detail names the Risk, how it was opened and its severity, and it replaces the old `RISK_STATUS_CHANGED` "auto-opened" event on a System, so one Risk gives one entry; an Organization Risk keeps that event), each written in the same transaction as the System or Risk (a System created before they existed shows a final "Created" entry from its creation date, without an actor), or a Provider's Control Offering added, changed or removed (#123), or the `"system"` event on each dependent whose effective status moved when a Provider's own status, Onboarded status, Offering or dependency changed (#124) — or System-less, for the evidence-bearing parts of the requirement database and the Organization's own implementations: a Control Mapping added, removed, or changed in Coverage; a Framework published; a Statement of Applicability justification changed; a Check-up evaluated; the status of an Organizational Control's Organization Control Implementation changed (one event per change, by the User who made it, nothing per System; a Both Control's change instead writes `"system"` events on the Systems whose effective status moved, #121; a Nonconformity's set-back of such an implementation is the same event, attributed to `"system"`, and a Nonconformity's Risk on a System is a `"system"` `RISK_LOGGED` event, #245, and for an Organization Risk a System-less `"system"` `RISK_STATUS_CHANGED` event, #157). *(Glossary change flagged for the product owner: the last System-less kind is new, #122.)* Deliberately not a full audit trail — other catalog curation (e.g. editing a Control's text) is out of scope. Attributed to either the acting User, or the literal actor `"system"` when the backend computed the change as a side effect of a different, human-initiated action (e.g. an inherited status change, or a Risk auto-opened by a "No" Self-Assessment answer).
_Avoid_: Audit log, Activity log (this app doesn't claim compliance-grade completeness — "Change Event" is the deliberately narrower term)
