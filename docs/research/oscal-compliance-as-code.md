# OSCAL and compliance as code

Researched 2026-11-23 against NIST's published model definitions and the current application.

**Recommendation.** Use OSCAL as the GRC tool’s versioned exchange format. Start with one System and generate an internal Control Catalog, a System Profile, a System Security Plan (SSP), and a print-ready SSP from the same snapshot. Validate the resolved control scope and trace a few implementation claims back to the System with an auditor. Use the existing Statement of Applicability (SoA) for Framework coverage across a Compliance Boundary. Add assessment and remediation exports as the next steps toward an evidence-backed posture report.

## What OSCAL provides

The Open Security Controls Assessment Language (OSCAL) specifies machine-readable models for control selection, implementation, assessment and remediation. NIST's latest stable model release is **v1.2.3** as of the research date. Its eight models serialize as JSON, XML or YAML. The release publishes JSON Schemas, XML Schemas and XML↔JSON converters. The JSON Schema also applies to the data obtained by parsing OSCAL YAML. This makes it possible to exchange and validate evidence packages while keeping the application and any policy checks in their existing tools. [NIST v1.2.3 release](https://github.com/usnistgov/OSCAL/releases/tag/v1.2.3) · [Versioned model reference](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/) · [Model overview](https://pages.nist.gov/OSCAL/learn/concepts/layer/overview/)

| OSCAL model | Purpose and fit in this app |
| --- | --- |
| **Catalog** | Defines the controls a baseline can select. Export the organization-authored Control Library as a catalog. A separate catalog for a Framework version can represent its Requirements if useful to the recipient and licensed for that use. Keep both identities even when base Controls and ISO Annex A Requirements share codes. [NIST Catalog](https://pages.nist.gov/OSCAL/learn/concepts/layer/control/catalog/) · [ADR 0005](../adr/0005-split-requirement-and-control.md) |
| **Profile** | Selects, merges and tailors controls from one or more catalogs or profiles. A profile for a System can select the actual applicable Controls from the internal Catalog. Profile resolution produces a tailored catalog, allowing CI to check the resulting control IDs. Effective Framework Scope is an input to the application's applicability rules, alongside classifications and Control scoping. [NIST Profile](https://pages.nist.gov/OSCAL/learn/concepts/layer/control/profile/) · [NIST profile resolution draft](https://pages.nist.gov/OSCAL/learn/concepts/processing/profile-resolution/) · [Effective Framework Scope](../../src/lib/effective-framework-scope.ts) |
| **Control Mapping** | Exchanges documented relationships between controls or statements in catalogs or profiles. Local `ControlMapping` records a Control's Full or Partial coverage of a Requirement. OSCAL relationships express source and target semantics with a matching rationale. Full coverage alone cannot establish equality, and Partial alone cannot establish subset versus overlap. Keep local coverage, gap acceptance and rationale as app semantics. Export a standard relationship only where its direction and meaning have been reviewed. [NIST v1.2.3 Control Mapping reference](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/mapping/json-reference/) · [Local schema](../../prisma/schema.prisma) |
| **Component Definition** | Describes reusable components and their suggested control implementations. Organization Control Implementations and Provider Offerings can seed reusable descriptions where there is enough implementation detail. For each System, the SSP must capture which responsibility is actually inherited or retained, with its source. Reuse the effective-status calculation and preserve its provenance, including System overrides and Shared Provider responsibilities. [NIST Component Definition](https://pages.nist.gov/OSCAL/learn/concepts/layer/implementation/component-definition/) · [ADR 0008](../adr/0008-providers-are-systems.md) · [Effective status](../../src/lib/effective-status.ts) |
| **System Security Plan (SSP)** | Describes a specific system, its baseline, boundary, implementation and control implementation. The required `import-profile` references the baseline Profile or a Catalog representing it. A System's description, Information Types, owners, Control Assessments and effective inheritance provide inputs. Confirm the technical authorization-boundary description, information types, operational status, component identities and implementation narratives for the pilot. [NIST SSP overview](https://pages.nist.gov/OSCAL/learn/concepts/layer/implementation/ssp/) · [v1.2.3 SSP structure](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/system-security-plan/json-outline/) |
| **Assessment Plan (AP)** | References a specific SSP via required `import-ssp`. It can express reviewed controls and objectives, subjects, assets, tasks and timing. Use a launched Internal Audit's selected scope and frozen Check-up questions as inputs for one System's plan. One Internal Audit may target multiple Systems and the Organization. Export each System's own plan against its SSP, and decide separately how to represent Organization-level work. [NIST Assessment Plan model](https://pages.nist.gov/OSCAL/learn/concepts/layer/assessment/assessment-plan/) · [v1.2.3 AP structure](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/assessment-plan/json-outline/) · [Local audit models](../../prisma/schema.prisma) |
| **Assessment Results (AR)** | References its plan via required `import-ap`. Records actual assessment activity, observations and evidence, and findings or risks where appropriate. A Check-up response is evidence with its author and date. The Internal Auditor's evaluation supplies a separate judgment about a defined control or objective. Preserve the differences between Conforming, Observation, Nonconformity, withdrawn and unanswered, and carry the linked Risk where one was opened. A System Owner self-assessment has its own provenance and assurance level. [v1.2.3 AR structure](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/assessment-results/json-outline/) · [App audit workflow](../../README.md#project-status) |
| **Plan of Action and Milestones (POA&M)** | Tracks weaknesses, risks, responses and disposition for a specific system. It can reference an SSP or identify the System by a unique `system-id`. The AR and POA&M share observation and risk structures, so a tracked Risk can keep its identity across the two documents. The app has a Risk owner, source, status, severity, likelihood, description and free-text mitigation plan. Structured remediation tasks, milestone dates and deadlines would need to come from an authoritative source before exporting them. Keep Organization Risks tied to their actual scope. [NIST POA&M model](https://pages.nist.gov/OSCAL/learn/concepts/layer/assessment/poam/) · [v1.2.3 POA&M structure](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/plan-of-action-and-milestones/json-outline/) · [ADR 0009](../adr/0009-a-risk-can-belong-to-the-organization.md) |

The app's Compliance Boundary may contain several Systems and Frameworks. Its SoA lists Framework Requirements, derives inclusion, records exclusion justifications, and shows the worst status across counted Systems. An SSP authorization boundary describes the scope of one system's implementation. Use the boundary memberships when calculating a System's effective Framework Scope, and supply a technical description for that System's SSP. The Boundary’s existing Provider perimeter can help identify dependencies for review. The SoA remains the audit view for cross-System applicability, exclusions and Requirement status. [ADR 0016](../adr/0016-compliance-boundaries-bring-frameworks-into-scope.md) · [Boundary SoA loader](../../src/lib/boundary-statement.ts) · [Boundary Provider perimeter](../../src/lib/boundary-perimeter.ts) · [v1.2.3 SSP structure](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/system-security-plan/json-outline/)

The SSP needs a reviewed account of how each Control works and who does the work. A Control Assessment status and a Self-Assessment answer can support that account. Waived and Not Applicable can count toward Requirement status under some Framework rules. Preserve the source disposition and its rationale, and use OSCAL `not-applicable` only for a justified applicability decision. Use `planned` only when there is an actual plan. Use recorded ATO information where the recipient’s authorization semantics match, and capture the System’s operational state explicitly. Retain the local Sensitivity Level and four-point Integrity and Availability scales until the recipient agrees on a categorization mapping. For licensed Frameworks, follow the app’s paraphrase policy and verify redistribution rights for any material included in the package. ## Security posture and audit outputs

Generate a System posture brief or a Compliance Boundary report as of a specific date. Show Framework Requirement coverage, with the applicable denominator and exclusions. Show when Controls were last assessed and by whom, which responsibilities were inherited or still owed, the latest Check-up outcomes, and open remediation. Show missing or outdated evidence visibly. Decide evidence freshness rules with the report owner. A change between snapshots can come from a scope change, an implementation change, or newly collected evidence. Report that reason alongside the change when the source records support it. OSCAL Assessment Results can carry timed observations and findings. The app can use those and its existing Boundary SoA calculations to produce the human report. [Boundary SoA loader](../../src/lib/boundary-statement.ts) · [Requirement status rules](../../src/lib/requirement-status-rules.ts) · [v1.2.3 Assessment Results](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/assessment-results/json-reference/)

For example, a directory Provider might implement privileged MFA and leave the System Owner responsible for disabling local bypass accounts. The SSP can show the Provider implementation and the customer obligation. A configuration check can record whether it found bypass accounts for a specific System and time. An evaluated Check-up can record the auditor’s finding. If that finding opens a Risk, the posture brief can show it as open and a later POA&M can carry the same Risk with an owner and an agreed remediation milestone. ## How the workflow would run

1. **Version the inputs.** Keep synthetic fixtures, exporter code, agreed mappings and rule changes reviewable in Git. Reuse the app's effective Framework Scope, applicability and effective-status rules for the export. Read a coherent snapshot in a transaction and apply object-level access to the System and each included resource. The Boundary SoA loader already uses a `RepeatableRead` transaction for consistent reads. [Effective Framework Scope](../../src/lib/effective-framework-scope.ts) · [Control applicability](../../src/lib/control-applicability.ts) · [Effective-status data](../../src/lib/effective-status-data.ts) · [Boundary SoA loader](../../src/lib/boundary-statement.ts) · [System visibility](../../src/lib/system-visibility.ts)
2. **Generate an attributable package.** Use stable control tokens and entity UUIDs across exports, with an explicit bridge from the app's CUIDs where UUIDs are required. Keep original Framework codes visible and avoid collisions across catalog sources. OSCAL uses a new root UUID and updated `last-modified` for changed document content, and retains both for serialization-only conversion. Save the released package and its provenance, including source revisions, exporter and schema versions and attachment digests, so an older review can be reproduced. The app's daily trend snapshots and replaceable uploaded files cannot reproduce a historical evidence bundle by themselves. [NIST identifiers](https://pages.nist.gov/OSCAL/learn/concepts/identifier-use/) · [NIST document identity and revisions](https://pages.nist.gov/OSCAL/learn/concepts/layer/overview/) · [Local schema](../../prisma/schema.prisma)
3. **Validate structure, references and meaning in CI.** Check JSON with each pinned v1.2.3 schema. Resolve the Profile and check that its selected controls match the app snapshot. Validate Metaschema constraints with a compatible tool or targeted tests, and check references across the full package, including control IDs, subjects, parties, components and evidence pointers. Add product assertions for scope, inherited responsibility, licensed text, and gaps left visible in the exported evidence. Validate any format or additional rules required by the recipient. NIST's published `oscal-cli` v1.0.3 release targets OSCAL v1.1.2. Evaluate the resolver pipeline in the v1.2.3 source tree. Verify the chosen resolver and constraint validator against pinned positive and negative fixtures before relying on them. [NIST validation guide](https://pages.nist.gov/OSCAL/learn/concepts/validation/) · [v1.2.3 model assets](https://github.com/usnistgov/OSCAL/releases/tag/v1.2.3) · [NIST CLI release notes](https://github.com/usnistgov/oscal-cli/releases/tag/v1.0.3) · [v1.2.3 resolver pipeline](https://github.com/usnistgov/OSCAL/tree/v1.2.3/src/utils/resolver-pipeline)
4. **Keep evidence reviewable.** OSCAL links can refer to external resources or package-local Back Matter. Publish only approved links and attachments, with audience, retention and access agreed. Resolve from a pinned local bundle in CI, with deliberate handling of external references. Preserve actor, date, source and any exclusions so an assessor can distinguish a policy check result, an owner's evidence submission and an auditor's finding. Where policy checks exist, record their rule version and tested target with the result. An assessor can then decide how the check counts toward a control objective. [NIST URI usage](https://pages.nist.gov/OSCAL/learn/concepts/uri-use/) · [v1.2.3 AR reference](https://pages.nist.gov/OSCAL-Reference/models/v1.2.3/assessment-results/json-reference/)
5. **Render from the same validated snapshot.** JSON is the machine exchange artifact. Produce a companion HTML view and print/PDF when an auditor needs one, using the same snapshot and cross-references so the two outputs agree. NIST publishes example XSLT for rendering Catalogs in HTML/PDF. An SSP, AR or POA&M view should be tested against the recipient's review needs. The app's existing SoA print view provides a local layout precedent. [NIST rendering examples](https://pages.nist.gov/oscal-tools/projects/xslt/) · [Boundary SoA print view](../../src/app/compliance-boundaries/[id]/statement/print/PrintBoundaryStatement.tsx)

## First pilot

Choose one representative synthetic or approved test System. Give it one locally implemented Control, one Control inherited from the Organization, a Shared Provider Offering with customer work still open, and an unmapped Framework Requirement. Use the last two cases to check that inheritance and the catalog selection leave coverage gaps visible in the auditor view. Use the internal Catalog, a pinned Profile selecting the relevant Control IDs, and an SSP describing the same System as a bundle of three linked JSON documents. Supply the System's boundary and component narrative explicitly. Compare the resolved control set and implementation provenance against the System detail view, validate with schemas plus reference checks, and render an HTML review from the same package. Include a broken-reference fixture to prove the checks catch a package that passes structural schema validation.

Agree with a prospective recipient which baseline, evidence fields and output format they will consume before using real System data. The pilot uses internal Control IDs. For a recipient that reviews a specific framework, use its accepted version and identifiers in the baseline and trace the same implementations via reviewed mappings. NIST publishes an OSCAL SP 800-53 catalog and baseline examples for interoperability testing. Recipient acceptance depends on the actual review rules and delivery format. [NIST OSCAL content](https://github.com/usnistgov/oscal-content) · [NIST profile resolution](https://pages.nist.gov/OSCAL/learn/concepts/processing/profile-resolution/)

For the next package, use a completed Internal Audit with a System in scope. That exercises the SSP → AP → AR chain and one linked Risk. Add a POA&M when the recipient’s required fields and the authoritative sources for dates, owners and milestones are known. This research checked the model definitions and the repository’s data and workflows. Running the resolver and generating the first package remain pilot acceptance checks.
